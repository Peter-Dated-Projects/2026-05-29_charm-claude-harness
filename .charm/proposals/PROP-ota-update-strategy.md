# PROP-ota-update-strategy

**Status:** draft
**Ticket:** T-014

---

## Problem

The charm harness is a multi-binary system (charmd daemon, MCP server, TUI console, CLI entry point, graph viewer). Shipping updates manually — by asking operators to `git pull && bun install` — is friction that will compound as charm matures. This proposal investigates the six main OTA update patterns for Rust desktop apps and recommends the right approach for charm's specific constraints.

---

## Charm-specific constraints

Before the comparison, the requirements that shape the recommendation:

| Constraint | Detail |
|---|---|
| Multi-component atomicity | An update must update all five binaries together, or none. A half-updated charm (new charmd, old MCP server) is worse than an outdated charm. |
| Daemon-safe | `charmd` may be running during the update check. The update must not interrupt a live session; the swap happens at next launch. |
| Human-gated | Updates must be user-confirmable, consistent with charm's philosophy. No silent background updates. |
| Distribution channel | charm is a developer tool. It does not live in an app store. GitHub Releases is the natural distribution point. |
| Platform scope | macOS-first, Linux-secondary. Windows is out of scope for now. |
| Rust rewrite target | The Rust rewrite proposal (`PROP-rust-rewrite.md`) sets the target architecture: static Cargo workspace binaries, no runtime. The OTA strategy must work in that world. |

## Mechanism survey

### 1. tauri-plugin-updater

**What it is:** The first-party updater bundled with the Tauri framework. It ships as a Rust plugin (`tauri-plugin-updater`) that calls home to a JSON endpoint, compares versions, downloads a signed bundle, and applies the update on restart.

**Server:** Requires a JSON update manifest endpoint. Can be GitHub Releases (with a release manifest file) or a custom server. The manifest format is documented; a simple static file host works. Tauri's own `tauri-update-server` is a reference implementation.

**Signing:** Uses ed25519 keypairs generated by `tauri signer generate`. The public key is embedded at build time; the private key signs every release artifact. Tauri verifies the signature before applying.

**Delta support:** No. Full-bundle only. The entire app bundle is re-downloaded on every update.

**Offline-first:** Yes in principle — the update check is a network call that can be deferred and retried. The plugin does not run on a background thread by default; the app code controls when to call `check_update()`.

**Framework integration:** Deep integration with Tauri only. Not usable with GPUI, Slint, Ratatui, or any non-Tauri framework.

**Licensing/cost:** Apache-2.0. Free. Self-hosted or GitHub Releases.

**Charm fit:** Poor. Charm is not (and likely will not be) a Tauri app. The Rust rewrite targets ratatui for the TUI. Even if it were Tauri, wrapping charmd and charm-mcp as sidecars inside a Tauri app bundle is architecturally awkward — Tauri's update model updates the entire `.app` bundle, which works for a GUI app but adds overhead for a daemon + CLI tool.

### 2. self_update crate

**What it is:** A Rust crate (`self_update`) that provides update-in-place logic for a single binary. Supports GitHub Releases as a backend, fetches the latest release matching a target triple, verifies SHA256/SHA512, and overwrites the running binary (on Windows via a rename trick; on Unix via atomic replace).

**Server:** GitHub Releases (built-in backend). Also supports HTTP endpoints with a custom `ReleaseList` format. No server-side code required; the crate fetches the GitHub API directly.

**Signing:** SHA256 or SHA512 checksum verification against a `.sha256` or `.sha512` file published alongside the release artifact. No asymmetric signing out of the box — checksum files must be trusted (i.e., fetched over HTTPS from a trusted origin).

**Delta support:** No. Full binary download.

**Offline-first:** Yes — the update check is a synchronous or async call the application controls. Easy to wrap in "check on reconnect" logic.

**Framework integration:** Framework-agnostic. Works in any Rust binary. Add the crate, call `self_update::backends::github::Update::configure().build()?.update()`.

**Licensing/cost:** MIT. Free.

**Charm fit:** Moderate for a single-binary tool; poor for charm's multi-binary architecture. The crate updates the binary it is called from. Charm would need to either (a) build a dedicated `charm-updater` binary that downloads and swaps all five binaries, or (b) call `self_update` from `charm-cli` with custom logic to also update charmd, charm-mcp, charm-console, and charm-graph. Workable but requires bespoke orchestration on top of the crate.

### 3. msitools / Squirrel / WiX

**What it is:** Windows installer-based update systems. MSI/WiX packages the application as a Windows Installer bundle; updates are delivered as new MSI packages or patch files (.msp). Squirrel (popularized by GitHub Desktop) wraps MSI/WiX with a simpler API and delta-patch support.

**Server:** Requires an update server (Squirrel's `Squirrel.Server` reference implementation or a custom endpoint). GitHub Releases can serve as the artifact store.

**Signing:** Authenticode code signing (Windows-standard). Requires a purchased code-signing certificate for distribution to end users without SmartScreen warnings.

**Delta support:** Squirrel supports NuGet delta packages. WiX supports MSI patch files (.msp). Both reduce download size for incremental updates.

**Offline-first:** Yes.

**Framework integration:** Windows-only. No direct Rust integration — these are OS-level packaging formats. A Rust app bundles its binaries inside an MSI; the installer framework handles the update logic outside the process.

**Licensing/cost:** WiX is MIT; Squirrel is MIT. Code-signing certificates cost $200-500/year.

**Charm fit:** Very poor. charm is macOS-first; Windows is out of scope. Even if Windows were in scope, WiX/Squirrel is appropriate for GUI apps installed system-wide, not developer CLI tools. Skip.

---

### 4. Sparkle / Homebrew Cask

**What it is:** Two distinct patterns for macOS:

- **Sparkle** is the de-facto OTA update framework for macOS `.app` bundles. It polls an `appcast.xml` feed, downloads update artifacts, verifies EdDSA signatures, and replaces the app bundle on disk. Used by thousands of macOS apps.
- **Homebrew Cask** is a package manager approach: instead of in-app updates, the user runs `brew upgrade charm` and Homebrew downloads and installs the new version.

**Server (Sparkle):** Any static HTTP host serving an `appcast.xml` feed. Can be GitHub Releases with a generated appcast. No dynamic server code required.

**Signing (Sparkle):** EdDSA (ed25519) via Sparkle's `generate_keys` tool. Public key embedded in the app bundle's Info.plist; private key signs release archives.

**Delta support (Sparkle):** Yes. Sparkle supports BinaryDelta patches — only the changed bytes between versions are downloaded. Delta generation is part of the release workflow (`generate_appcast` produces delta files).

**Offline-first:** Yes. Sparkle's check is a background network call; reconnect-triggered checks are supported.

**Framework integration (Sparkle):** macOS `.app` bundle only. Written in Objective-C/Swift. Integration from Rust requires calling the Sparkle framework via Objective-C FFI or via a thin Swift/ObjC wrapper. Non-trivial for a command-line daemon.

**Homebrew Cask:** No server required; the Homebrew formula repo is the distribution channel. No in-app update logic — entirely managed outside the process. Simple and safe but requires the user to actively upgrade.

**Licensing/cost:** Sparkle is MIT. Homebrew Cask is BSD-2-Clause. Both are free.

**Charm fit for Sparkle:** Poor. Sparkle is built for macOS `.app` bundles with a GUI lifecycle (launch, background check, user prompt via native dialog). charm's components are CLI/daemon processes, not an `.app` bundle. The FFI complexity from Rust is significant. Delta updates are attractive but not worth the framework mismatch.

**Charm fit for Homebrew Cask:** Good as a distribution channel (complementary to OTA, not a replacement). The operator population installs via `brew install` or from a GitHub release tarball. Homebrew is the right way to get charm onto a new machine, but it is not an in-product update mechanism.

### 5. Custom: download + atomic swap

**What it is:** The charm-native approach. The CLI (or a dedicated `charm update` subcommand) checks GitHub Releases for a newer version, downloads a release tarball, verifies a signature, stages the new binaries to a `.charm/updates/<version>/` directory, and at next `charm start` atomically replaces the active binaries via `std::fs::rename` (which is atomic on POSIX filesystems within the same mount point).

**Server:** GitHub Releases as the artifact store. A small JSON manifest file (e.g., `latest.json`) published alongside each release describes the latest version, download URL, and SHA256 digest. No server-side compute required. GitHub's API can also serve as the manifest.

**Signing:** Two-tier verification:
1. SHA256 digest of the release tarball, published in `latest.json` and also as a standalone `.sha256` file.
2. Optional: ed25519 signature over `latest.json` itself, verified against a public key embedded in the binary. This catches MITM attacks on the manifest.

**Delta support:** No native delta support. Can be added later by producing binary diff files (bsdiff/zstd-patchelf) and publishing them alongside the release, but the implementation complexity is significant. For a developer tool updated infrequently, full-bundle is acceptable.

**Offline-first:** Trivially yes. The check is a single HTTPS GET; wrap it in a timeout with fallback to the cached current version.

**Framework integration:** Framework-agnostic. The update logic lives entirely in `charm-cli`. It does not touch charmd or the TUI. No dependency on any UI toolkit.

**Multi-component atomicity:** This is where the design earns its place for charm. The release artifact is a single tarball containing all five binaries. The download stages the entire tarball to `.charm/updates/<version>/`. At `charm start`, the launcher checks for a staged update, verifies it (signature + digest), and performs a single atomic directory rename from `.charm/updates/<version>/` to the install location. All five binaries flip together or none do. A failed rename (disk full, permissions error) leaves the old binaries intact.

**Daemon-safe:** The daemon does not participate in the update check or application. The `charm start` command (which users run to begin a session) checks for a staged update before launching any processes. If a session is already running, the update is deferred to the next `charm start`. No running process is interrupted.

**User-confirmable:** The `charm update` subcommand (or the `charm start` pre-flight check) prints the new version's release notes and prompts for confirmation before downloading or applying. Consistent with the human-gated philosophy.

**Licensing/cost:** No third-party dependencies beyond the standard Rust HTTP client (`reqwest` + `tokio` or `ureq` for a sync variant) and a signature library (`ed25519-dalek`). MIT/Apache-2.0 throughout. GitHub Releases is free for public repos; for private repos, the GitHub API requires a token (trivial for a developer tool).

**Charm fit:** Excellent. This is the approach to build.

### 6. Nix / Flatpak / AppImage auto-update

**What it is:** Linux packaging formats that include their own update semantics.

- **AppImage + AppImageUpdate:** An AppImage bundles the entire application (including dependencies) into a single squashfs file. AppImageUpdate applies zsync-based binary deltas to update an existing AppImage in place. The delta mechanism is mature and genuinely saves bandwidth. Supported by `appimageupdatetool`.
- **Flatpak:** OSTree-based flatpak repos deliver delta updates. Updates are managed by the system Flatpak daemon, not the app itself. User runs `flatpak update`.
- **Nix flakes:** A Nix flake publishes each version as a derivation. Users run `nix flake update` or `nix profile upgrade`. No in-app update logic.

**Server:** AppImage uses zsync servers (can be GitHub Releases with `.zsync` metadata). Flatpak requires a Flatpak repo (Flathub or self-hosted). Nix uses the Nix cache infrastructure.

**Signing:** AppImage: no mandatory signing (but GPG can be used). Flatpak: GPG keys required for the repo. Nix: content-addressed; signatures are optional but supported.

**Delta support:** AppImage: yes (zsync). Flatpak: yes (OSTree). Nix: yes (content-addressed, only changed paths are fetched).

**Offline-first:** Yes for all three.

**Framework integration:** These are packaging formats, not libraries. A Rust binary built with Cargo can be packaged as any of these; no code changes required inside the binary.

**Charm fit:**
- AppImage is interesting as a Linux distribution format (bundles the entire runtime, no dependency hell). For a developer tool targeting Linux operators, AppImage is a reasonable download format alongside the raw tarball. AppImageUpdate's zsync delta mechanism is the most mature delta OTA story available without writing it yourself.
- Flatpak and Nix are better fits for end-user desktop apps than for a developer CLI daemon tool. They add infrastructure overhead and assume a managed system environment.
- Recommendation: offer an AppImage alongside the tarball release for Linux, with AppImageUpdate support. Do not make Flatpak or Nix a primary distribution channel.

## Recommendation

**Build a custom update mechanism using GitHub Releases as the artifact store, with an AppImage variant for Linux delta updates.**

### Why custom over an existing crate

None of the existing crates or frameworks solve charm's specific problem cleanly:
- `self_update` updates one binary; charm has five.
- Tauri/Sparkle are tightly coupled to GUI app bundle formats.
- The business logic for charm's update flow (stage to `.charm/updates/`, confirm at next `charm start`, swap atomically) is simple enough that building it is less work than adapting an existing tool.

### Architecture

#### Release artifact

Each GitHub release publishes:
```
charm-v1.2.0-aarch64-apple-darwin.tar.gz    # macOS ARM tarball
charm-v1.2.0-x86_64-apple-darwin.tar.gz     # macOS Intel tarball
charm-v1.2.0-x86_64-unknown-linux-gnu.tar.gz # Linux tarball
charm-v1.2.0-aarch64-apple-darwin.tar.gz.sha256
charm-v1.2.0-x86_64-unknown-linux-gnu.AppImage  # Linux AppImage
latest.json                                  # version manifest
```

`latest.json` structure:
```json
{
  "version": "1.2.0",
  "pub_date": "2026-06-16T00:00:00Z",
  "notes": "Release notes text here.",
  "platforms": {
    "darwin-aarch64": {
      "url": "https://github.com/owner/charm/releases/download/v1.2.0/charm-v1.2.0-aarch64-apple-darwin.tar.gz",
      "sha256": "abc123..."
    },
    "darwin-x86_64": { ... },
    "linux-x86_64": { ... }
  },
  "signature": "<ed25519 signature over the rest of this JSON>"
}
```

The `signature` field is an ed25519 signature over the JSON body (excluding the `signature` key itself), signed with the release private key. The public key is embedded in the `charm-cli` binary at build time via a `const` or environment variable baked in by the CI pipeline.

#### Update flow

1. **Check:** `charm update check` (or automatic pre-flight in `charm start`) fetches `latest.json` from GitHub Releases over HTTPS. Verifies the ed25519 signature. Compares the version against the currently-installed version.

2. **Prompt:** If a newer version is available, prints the version number and release notes. Asks for confirmation: `Update charm from v1.1.0 to v1.2.0? [y/N]`.

3. **Download:** Downloads the tarball to a temp file. Verifies the SHA256 digest against `latest.json`. Extracts to `.charm/updates/<version>/`.

4. **Stage:** Writes a `.charm/updates/pending` marker file pointing to the new version directory.

5. **Apply (at next `charm start`):** The launcher reads `.charm/updates/pending`. If present and the daemon is not running, atomically renames all staged binaries into the install path using `std::fs::rename`. On failure (same-filesystem rename is atomic on POSIX; cross-filesystem is not), falls back to a `copy + fsync + rename` dance. Clears the pending marker on success.

6. **Daemon-safe:** If `charm start` detects a running session (`charmd` is alive on the session socket), it skips the update and prints: `Update staged. Will apply at the start of the next session.`

#### Key infrastructure

One ed25519 keypair. The private key lives in the CI/CD environment as a secret (never committed). The public key is a 32-byte constant embedded in the `charm-cli` binary. Key rotation requires a new release with the new public key, which is acceptable for a developer tool.

#### Linux AppImage

For Linux operators, the AppImage variant packages all five binaries (plus any shared library dependencies) into a single squashfs bundle. AppImageUpdate's zsync support means that after the initial download, only changed file-system blocks are fetched on update — typically 5-15% of the full bundle size for minor versions.

The AppImage update check integrates with the same `latest.json` manifest (adding an `appimage` key to the `linux-x86_64` entry pointing to the AppImage artifact and its zsync file). The `charm update` command detects whether it is running from within an AppImage and uses `appimageupdatetool` for the apply step.

### What this does not solve

- **Rollback:** A failed update (corrupted download caught by SHA256 verification) simply does not apply — the old binaries remain. But a successfully-applied bad release requires the operator to manually download an older version. Rollback support (keeping a `previous/` snapshot) is a future enhancement.
- **Auto-update without user action:** Intentionally not implemented. charm is a human-gated system; silent auto-update contradicts that. An `--auto-apply` flag can be added later for CI environments.
- **Windows:** Out of scope. If Windows support is ever needed, WiX/MSIX is the right packaging format at that point.

## Implementation sketch (Rust rewrite context)

In the Rust rewrite's `charm-core` crate, add `update.rs`:

```rust
pub struct UpdateManifest {
    pub version: semver::Version,
    pub pub_date: chrono::DateTime<Utc>,
    pub notes: String,
    pub download_url: String,
    pub sha256: [u8; 32],
    pub signature: [u8; 64],  // ed25519 over the rest
}

pub async fn check_for_update(current: &semver::Version) -> Result<Option<UpdateManifest>>;
pub async fn download_update(manifest: &UpdateManifest, staging_dir: &Path) -> Result<PathBuf>;
pub fn apply_staged_update(staging_dir: &Path, install_dir: &Path) -> Result<()>;
```

`charm-cli`'s `start` subcommand calls `check_for_update` and `apply_staged_update` in sequence before spawning `charmd`. The `charm update` subcommand calls the full flow interactively.

Dependencies added to `charm-core`:
- `reqwest` or `ureq` (HTTP client, async or sync)
- `ed25519-dalek` (signature verification)
- `sha2` (SHA256 digest)
- `semver` (version comparison)
- `tar` + `flate2` (tarball extraction)

Total new code: ~400 lines. No new services required beyond GitHub Releases.
