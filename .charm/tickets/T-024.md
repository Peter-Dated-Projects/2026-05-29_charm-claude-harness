## Component-by-component analysis

### 1. charmd (daemon) — `src/daemon/`

**What it does today:**
The long-running brain. Owns the ticket store (gray-matter .md files + bun:sqlite index), the in-memory agent registry, the dependency+file-scope solver (graphology), the COORDINATION.md writer, and all tmux pane management. Listens on a per-session Unix domain socket at `.charm/run/<uuid>/sock` (or a tmpdir fallback if the path is too long). Speaks a newline-delimited JSON-RPC protocol: `{ id, method, params }` requests, `{ id, ok, result, error }` responses (see `src/daemon/rpc.ts`).

**Tmux coupling in the daemon (the key inventory):**
The daemon has exactly these tmux touch-points, all in `src/daemon/index.ts`:
- `spawnAgentLocked` — calls `tmux.splitPane()` to create a new pane and get back a stable pane id.
- `tearDownAgent` — calls `tmux.killPane()`.
- `sweepDeadPanes` (15s sweep) — calls `tmux.listPanes()` and checks `pane.dead` to detect agents that exited without reporting.
- `relayoutLocked` — calls `tmux.windowSize()`, `tmux.paneIndex()`, `tmux.paneWidth()`, `tmux.applyLayout()` to rebuild the VS-Code-style grid.
- `pingOrchestrator` — calls `tmux.sendText()` to inject "[charm] <event>. Reap finished panes..." into the orchestrator's live pane (the wake signal when sub-agents change state).
- `continue_agent` RPC handler — calls `tmux.sendText()` to inject the orchestrator's guidance into a blocked agent's pane.
- `set_mode` RPC handler — calls `tmux.sendText()` to inject `/model <id>` and a follow-up message into the orchestrator's pane.
- `spawn_suborchestrator` — calls `tmux.newWindow()` to open a dedicated window.

The rest of the daemon (ticket store, registry, solver, approvals, coord writer, session lifecycle) is **100% tmux-free**. The socket protocol is already a clean, tmux-agnostic IPC interface.

**Equivalent in a native IDE:**
The daemon socket is the interface. A Tauri/Zed frontend connects to the same Unix socket and issues the same JSON-RPC calls. The daemon needs a pluggable "pane backend" abstraction: the eight tmux touch-points above map to abstract operations (create_terminal, kill_terminal, list_terminals, inject_text, get_terminal_size, relayout) that a tmux backend or a native-PTY backend can implement.

### 2. charm-mcp (MCP shim) — `src/mcp/server.ts`

**What it does today:**
A thin stdio MCP server spawned by every `claude` process via `.charm/charm.json` (or the per-session `sessionMcpConfig`, which has `CHARM_SOCKET` baked into its env block). Reads `CHARM_SOCKET` and `CHARM_AGENT_ID` from env. Exposes ~20 charm tools to agents and forwards each as an RPC call to the daemon over the Unix socket. Zero UI logic; zero tmux knowledge.

**Equivalent in native IDE:**
Unchanged. Every agent is still a `claude` process launched with `--mcp-config` pointing at a config whose env block carries `CHARM_SOCKET`. The shim stays exactly as-is. This is the agent-to-daemon bridge and is already IDE-agnostic.

---

### 3. charm-console (Ink TUI) — `src/console/app.tsx`

**What it does today:**
An Ink (React-for-terminal) app pinned to the left pane of the tmux session. Four tabs:
- **Artifacts** — file list (PROJECT.md, COORDINATION.md, tickets/*.md) with auto-selection based on pipeline stage, plus a markdown viewer. Uses chokidar for fs-watched auto-refresh.
- **Approvals** — lists pending gates from the daemon (polled every 1500ms via `rpcCall(socket, "status")`); y/n keys call `approve_gate` RPC.
- **Agents** — lists registry agents with dismiss (d) and kill (x·x) actions.
- **Files** — full project file tree browser with binary detection.

The console is a pure RPC client: it only talks to the daemon via the socket. It never touches tmux directly.

**Equivalent in native IDE:**
The console maps cleanly to a native sidebar panel. Each tab becomes a panel section or a tabbed view:
- Artifacts tab -> a file/ticket browser panel with markdown preview
- Approvals tab -> a notification/action panel with approve/reject buttons
- Agents tab -> a process/fleet status panel
- Files tab -> an embedded file explorer (potentially redundant with IDE's own tree)

The socket polling (`useStatus` calls `rpcCall` every 1500ms) is simple to replicate. The chokidar watches could be replaced by daemon-push events (the daemon already writes COORDINATION.md on every state change; a native frontend could subscribe to file changes or an SSE/WebSocket the daemon exposes).

### 4. charm CLI — `src/cli.ts`

**What it does today:**
`init` / `start` / `stop` / `attach` / `resume` / `status` / `approve` / `restart` / `reset-kb` / `worktree` / `tree` / `ctl`.

The most tmux-heavy command is `start`:
1. Creates a tmux session via `tmux.newSession()`
2. Spawns charmd (detached background process)
3. Waits for the daemon socket
4. Creates the console pane via `tmux.spawnInWindow()`
5. Splits the main agent pane via `tmux.splitPane()`
6. Calls `register_panes` RPC to tell the daemon which panes belong to which role
7. Binds the `:` key via `tmux.bindCommandPrompt()`
8. Selects focus to the main agent pane

`resume` relaunches the orchestrator's claude conversation via `tmux respawn-pane -k` in the existing pane.
`ctl` handles the `:q`/`:a`/`:dev`/`:research`/`:so` commands from the tmux key binding.
`stop` kills graph viewers, sends `shutdown` RPC, kills the tmux session.

**Equivalent in native IDE:**
- `init` — unchanged (filesystem setup; no tmux).
- `start` — becomes "open charm session" in the IDE: starts the daemon, then tells the IDE to create terminal tabs for the console and main agent. The `:` key binding goes away entirely (replaced by IDE commands/buttons).
- `stop`/`attach`/`status` — remain as CLI commands; the daemon socket interface is unchanged.
- `approve` — remains CLI; calls `approve_gate` RPC.
- `ctl` — replaced by IDE commands.
- `resume` — needs PTY-level respawn, same challenge as `start`.

### 5. tmux.ts + layout.ts — `src/daemon/tmux.ts`, `src/daemon/layout.ts`

**What it does today:**
`tmux.ts` is the full tmux wrapper: newSession, splitPane, killPane, sendText, listPanes, paneAlive, paneIndex, paneWidth, applyLayout, bindCommandPrompt.

`sendText` is the most architecturally important: it uses `tmux set-buffer` + `paste-buffer -p` + `send-keys Enter` to inject text into a running pane atomically (bracketed paste so multi-line messages land intact). This is how the daemon wakes the orchestrator and unblocks agents.

`layout.ts` builds a tmux custom-layout string for the VS-Code-style grid: console column pinned left, orchestrator column with a minimum-width guarantee, sub-agents in a 2-row grid filling the right. The checksum computation (`layout_checksum` in tmux C source) is re-implemented in TS.

**Equivalent in native IDE:**
`tmux.ts` needs a complete replacement — a "terminal backend" interface with the same operations but implemented against whatever the IDE exposes. `layout.ts` is entirely replaceable with the IDE's native panel layout API (and the checksum computation is only needed for tmux custom layouts, so it disappears entirely).

---

### 6. spawn.ts — `src/daemon/spawn.ts`

**What it does today:**
Builds the shell command string run in each tmux pane:
```
export CHARM_AGENT_ID=<id>
export CHARM_SOCKET=<socket>
export CLAUDE_CODE_SKIP_PROMPT_HISTORY=1
export MAX_THINKING_TOKENS=<n>
exec claude --session-id <uuid> --model <m> --permission-mode auto \
  --mcp-config <sessionMcpConfig> \
  --disallowed-tools Agent Task Workflow \
  --append-system-prompt <rolePrompt+rules> \
  <initial-prompt>
```

The role-specific system prompt is loaded from `.charm/prompts/<role>.md` and combined with shared rules (no-emoji, no-subagent, coordination ethos).

**Equivalent in native IDE:**
The command string is unchanged. The only thing that changes is WHERE it runs (an IDE terminal tab instead of a tmux pane). The env vars, flags, and system prompt assembly are all IDE-agnostic.

---

### 7. Ticket store, schema, paths — `src/store/tickets.ts`, `src/schema.ts`, `src/paths.ts`

**What they do today:**
- `paths.ts` resolves all file paths for a session (socket, db, tickets, coordination, etc.). Fully portable.
- `schema.ts` defines zod schemas for tickets, agents, approvals, RPC envelopes. Fully portable.
- Ticket store: gray-matter parsing of .md files + bun:sqlite index (frontmatter only; body is free-form). The source of truth is always the .md files; sqlite is rebuilt from them on daemon boot.

**Equivalent in native IDE:**
Unchanged entirely. The .md+sqlite model is filesystem-based; any backend that can read/write files works. The daemon owns this layer.

## The IPC surface (question 5)

The daemon exposes a **Unix domain socket** at `.charm/run/<uuid>/sock` (or tmpdir for long paths). Protocol: newline-delimited JSON, one request per line, one response per line, correlation by `id`. The full method set is: `ping`, `status`, `list_tickets`, `approve_gate`, `pending_approvals`, `register_panes`, `create_tickets`, `promote`, `create_proposal`, `list_proposals`, `finish_proposal`, `spawn_investigators`, `spawn_workers`, `create_worktree`, `list_worktrees`, `close_worktree`, `await_approval`, `update_plan`, `read_coordination`, `report_status`, `set_ticket_status`, `set_ticket_state`, `dismiss_agent`, `kill_agent`, `cancel_ticket`, `continue_agent`, `orchestrator_pane`, `list_agents`, `set_session_description`, `set_mode`, `shutdown`, `open_graph`, `spawn_suborchestrator`.

**Can a Zed extension or GPUI app connect directly?**
Yes — and this is already the pattern the console uses. `app.tsx` is a pure socket client: `rpcCall(PATHS.socket, "status")` etc. A Zed extension or a Tauri/GPUI app can do the same thing. The daemon has no knowledge of or dependency on who is on the other end of the socket.

The charm-mcp shim is specifically the `claude` process -> daemon bridge. A native UI frontend does NOT go through charm-mcp; it connects to the daemon socket directly. charm-mcp is only needed for claude agents.

The socket is a Unix domain socket, so a Rust client in a Tauri backend, or a Node/TS Zed extension, can both connect. The protocol is simple enough (newline-delimited JSON) to implement in any language.

## Top 5 hardest migration challenges

### 1. Text injection into running claude processes (hardest)

The daemon's `pingOrchestrator` and `continue_agent` work by injecting text into a running tmux pane via bracketed paste. This is how:
- The orchestrator learns a sub-agent finished (the wake signal after every `report_status(done/failed/blocked)`)
- The orchestrator's guidance reaches a blocked agent (`continue_agent`)
- Mid-session model swap sends `/model <id>` to the orchestrator's live REPL

In tmux, this is `tmux paste-buffer -p` + `send-keys Enter`. In a native IDE:
- **node-pty**: write to the PTY master fd; this works but requires the daemon to hold the master fd for each agent's terminal
- **Zed extension API**: Zed does not currently expose a "write to terminal input" extension API; this would require either a Zed upstream change or running tmux as the PTY backend behind the Zed terminal
- **Tauri + xterm.js**: the Tauri backend could manage PTYs directly (via a Rust pty crate) and write to them; the xterm.js frontend just renders the output

The bracketed paste mechanism was specifically added because plain `send-keys -l` broke on multi-line messages. Any replacement must handle multi-line text injection correctly.

### 2. Per-agent PTY management

Each `claude` agent is a full interactive Claude Code session — it renders its own Ink TUI, manages its own input loop, and requires a real PTY with proper dimensions. The daemon currently creates one tmux pane per agent and gets back a stable pane id. The pane id is used to:
- Kill the agent (`tmux kill-pane`)
- Check liveness (`tmux list-panes` + `pane_dead` flag)
- Send text (injection above)
- Relayout the grid

In a native IDE, each agent needs its own terminal tab/panel with a PTY. The handle for that terminal (equivalent to tmux's pane id) must be stable and accessible to the daemon for the lifecycle operations above. This requires the IDE to expose a "spawn terminal with PTY, return stable handle" API, which Zed's extension system may not provide today.

### 3. The liveness sweep

The daemon runs a 15-second sweep (`sweepDeadPanes`) that calls `tmux list-panes` with `#{pane_dead}` to detect agents that exited without calling `report_status` (crash, OOM, kill -9). A two-streak filter (seen dead twice before reaping) prevents racing a normal teardown.

Replacement requires: an exit-event mechanism per PTY. With node-pty you get an `exit` event; with a Rust pty crate in Tauri, same. The daemon can subscribe to process-exit events instead of polling. This is actually cleaner than the current sweep — event-driven instead of poll-based — but requires rearchitecting the sweep into an event subscription model.

### 4. await_approval and long-lived blocking RPCs

The orchestrator calls `await_approval(stage=2, label=...)` which blocks indefinitely in the MCP shim until a human resolves the gate. The daemon's ApprovalQueue stores the Promise and resolves it when `approve_gate` RPC arrives from ANY client (the console, the CLI, or a future native UI). This long-poll is currently handled cleanly because the claude process and its MCP shim live in a tmux pane that stays up for the session.

In a native IDE, if the UI is a separate process (Tauri app) that the user can close and reopen, the blocking promise in the MCP shim still works — the shim stays alive in a terminal tab as long as claude is running. The gate is daemon-side state (in-memory ApprovalQueue), so it survives the UI being closed and reopened. The gap is: if the daemon restarts (crash + resume), in-memory gates are lost, and any await_approval call that was blocking gets a closed socket. This is a pre-existing limitation not specific to the native IDE migration.

### 5. register_panes and orchestrator tracking

When `charm start` creates the tmux session, it calls `register_panes` RPC to tell the daemon which pane is the console and which panes are agents. The daemon tracks `consolePaneId`, `agentPaneIds`, and `orchestratorPaneId` in memory. These pane ids are used for:
- Relayout decisions (which panes to include in the grid)
- pingOrchestrator (which pane to wake)
- Dead-pane sweep (which panes are known vs. orphan)
- `charm resume` (relaunch into the exact pane id)

In a native IDE, the "pane registration" ceremony still needs to happen — the daemon needs to know which terminal handle is the console vs. the orchestrator vs. each sub-agent. The socket-based `register_panes` RPC already provides this abstraction; only the concrete handle type changes (tmux pane id -> IDE terminal handle). The `orchestrator_pane` RPC (used by `charm resume`) needs to return whatever handle the IDE uses.

## What a worker will need

**Entry points:**
- `src/daemon/index.ts` lines ~309-423 (pane tracking state, `spawnAgentLocked`, `tearDownAgent`) — the core tmux coupling to replace
- `src/daemon/tmux.ts` — complete replacement (new terminal backend module)
- `src/daemon/layout.ts` — complete replacement (IDE panel layout)
- `src/cli.ts` lines ~78-261 (the `start` command) — partial replacement of pane creation
- `src/console/app.tsx` — complete replacement with native UI

**Interfaces/contracts to honor:**
- The Unix socket JSON-RPC protocol is the stable interface; the frontend changes but the daemon API does not
- `register_panes` RPC must remain: callers (the `start` equivalent) register terminal handles with the daemon
- The `agent_pane_ids` in `register_panes` and the `pane_id` field on Agent records become whatever the IDE terminal handle type is (still a string)
- `CHARM_AGENT_ID` + `CHARM_SOCKET` env vars are still required on each claude spawn; the command string from `spawn.ts` is unchanged

**Recommended approach:**
Extract a `TerminalBackend` interface with these methods:
- `createTerminal(cmd, cwd) -> Promise<string>` (returns stable handle id)
- `killTerminal(id) -> Promise<void>`
- `sendText(id, text) -> Promise<void>` (must handle multi-line correctly)
- `listTerminals() -> { id, dead, pid }[]`
- `getTerminalDimensions(id) -> { w, h } | null`

Then the daemon's tmux calls become calls to this interface. A `TmuxBackend` implements it (current code), and a `NativeBackend` implements it for the IDE target. The daemon itself never imports `tmux.ts` directly after this refactor — it imports the `TerminalBackend` type.

This is a clean, bounded refactor with no changes to ticket store, solver, approvals, or any agent-facing MCP behavior.

**Files a build ticket would touch:**
- `src/daemon/tmux.ts` (rewrite as interface + TmuxBackend implementation)
- `src/daemon/layout.ts` (replace or make optional)
- `src/daemon/index.ts` (inject TerminalBackend instead of hardcoded Tmux calls)
- `src/cli.ts` (replace the tmux session/pane bootstrap in `start`)
- `src/console/app.tsx` (replace with native UI — separate ticket likely)

**Edge cases / gotchas:**
- The `register_panes` RPC call comes from the CLI/IDE side, not from agents; the daemon must NOT require tmux to be available before it can receive this call (already the case — the daemon starts without tmux and logs a warning)
- The `set_mode` handler injects text into the orchestrator's live pane to swap the model mid-session; a native implementation must do the same or the mid-session model swap feature breaks
- `charm resume` (`tmux respawn-pane -k`) is the hardest CLI operation to port — it relaunches claude in the SAME terminal handle as before. With node-pty this means closing the old process and spawning a new one on the same PTY fd or a new one at the same screen position; with Zed it may mean sending a shell command to the terminal tab
- Per-session MCP config (`sessionMcpConfig`) is critical for isolation: each session's agents must get a config with THIS session's `CHARM_SOCKET` in it. This is already done correctly in the daemon; just don't break it during the port

Top migration challenges **1. Agent spawning without tmux (hardest)** `spawnAgentLocked()` calls `tmux.splitPane()` which both launches the `claude` process and creates the visible terminal pane in one atomic operation. In a native IDE, these must be decoupled: the daemon spawns `claude` as a child process (managing PID + stdin/stdout), and the IDE creates a terminal panel that attaches to that process's PTY. The daemon needs a new abstraction: a "pane provider" interface that accepts a command+env and returns a handle, with the tmux implementation kept as one backend and IDE terminal as another. The liveness sweep also changes: instead of querying `tmux list-panes --pane_dead`, it watches process-exit events directly. **2. `continue_agent` — injecting text into a blocked agent (second hardest)** The orchestrator resumes a blocked agent by calling `continue_agent`, which calls `tmux.sendText(paneId, message)` — typing text into a live interactive `claude` REPL. In a native IDE terminal panel, the equivalent is writing to the PTY's master fd. This is achievable (every terminal emulator does it), but the current abstraction is purely tmux-level. The daemon needs a PTY handle or a write-to-process API. In Tauri, this means the Rust backend holds a `tokio::process::Child` with a `pty_master` fd and exposes a `send_to_agent(agent_id, text)` command. In GPUI, the Terminal component exposes input injection. This is NOT achievable for Zed extensions (they cannot control running terminal processes). **3. Approval gate UX — synchronous blocking in an async GUI** `await_approval` is a blocking RPC: the daemon parks until the human resolves the gate. In the Ink TUI this works trivially — y/n is a keystroke in the same process. In a native IDE, the UI needs to surface the gate as a modal or notification, the user clicks approve/reject, and the click fires `approve_gate` on the socket. The daemon side is unchanged (it already uses `approvals.enqueue()` which returns a Promise that resolves when `approvals.resolve()` is called). The UI challenge is making sure the gate is surfaced prominently enough that the operator doesn't miss it — the Ink TUI auto-switches to the Approvals tab when `pendingCount > 0`. The native app needs an equivalent nudge (notification badge, modal, or panel focus change). **4. Multi-session management — no sessions manifest in charmd** The current model is one `charm start` = one tmux session = one charmd = one session UUID. The operator sees all agents in one window and `:q` tears down exactly that session. In a native IDE, the operator might want to see multiple sessions (Orchestrator Hub). charmd currently has no RPC to enumerate all live sessions in a directory — each daemon only knows about itself. Building the Hub requires either: (a) a new charmd RPC that reads `.charm/run/*/meta.json` files and aggregates them, or (b) a separate session-registry process. This is a build-new item. **5. Streaming agent output — terminal rendering vs. IDE terminal panel** Each `claude` agent streams its output to the tmux pane via ANSI/VT100 escape sequences. The Ink TUI does NOT render this — it only shows COORDINATION.md and ticket files. The operator watches agents stream by switching between tmux panes. In a native IDE, each agent needs a terminal panel (xterm.js in Tauri, GPUI Terminal, Zed terminal tab) that renders the PTY output. The challenge is lifecycle: the IDE must create a terminal panel for each spawned agent, keep it alive as long as the process runs, and surface it for operator inspection. This maps to the same "pane provider" abstraction as challenge 1. The Tauri approach can use `xterm.js` WebView components per agent; this is well-trodden territory. --- ### 6. Recommended migration path The right foundation is Tauri v2 + React (confirmed by T-025). The migration strategy in order of dependency: **Phase 1 (no charmd changes required):** Wire the existing Tauri Rust IPC to the charmd Unix socket. Read `status`, `list_tickets`, `list_agents`, `read_coordination` to populate the studio UI. Wire `approve_gate` to the approvals UI. This alone makes the studio a live read/write console with approval gates — replacing the Ink TUI for the operator's view of the fleet. **Phase 2 (charmd minor additions):** Add a sessions-manifest RPC (read `.charm/run/*/meta.json`, return live sessions) for the Orchestrator Hub. This is a pure charmd addition with no interface-breaking changes. **Phase 3 (charmd pane-provider abstraction):** Extract the tmux coupling into a `PaneProvider` interface. Implement two backends: the current tmux backend (keeps backward compatibility) and a new "pty-direct" backend that spawns `claude` as a child process with a PTY and exposes read/write handles to the Tauri Rust layer. The Tauri backend creates `xterm.js` panels for each agent and wires them to the PTY fds. `continue_agent` changes from `tmux.sendText` to writing to the PTY master fd. **Phase 4 (remove tmux dependency):** With the pty-direct backend working, the tmux backend becomes optional. Add a `CHARM_NO_TMUX=1` flag. Users on macOS with the Tauri app set this; users who prefer the terminal keep tmux as the default. This path preserves full backward compatibility at each step and ships value (live UI) before the hard work (PTY management) is done.
