## Context

charm's native app is Tauri v2 (Rust backend) + React frontend. The existing charm daemon (`charmd`) is a TypeScript/Bun process exposing a Unix domain socket JSON-RPC server. The React frontend needs real-time updates of the agent graph state to drive the React Flow canvas.

All output from this ticket goes to the `charm/native-ui` worktree. Write proposals to `.charm/worktrees/native-ui/.charm/proposals/` and track notes to `.charm/worktrees/native-ui/.charm/kb/tracks/native-ui/`. Do NOT write to the main `.charm/proposals/` directory.

## What to design

### 1. Frontend data model
Define the TypeScript types the React app works with:
- `AgentNode` — id, role, state, ticketId, worktreeContext, spawnedBy, spawnedAt, logBuffer
- `TicketNode` — id, title, status, stage, dependsOn, touches
- `ApprovalGate` — gateId, agentId, message, requestedAt
- `SessionState` — sessionId, model, startedAt, agents[], pendingGates[]
- `GraphState` — nodes (AgentNode[]), edges (spawn relationships)

How does the graph state map to React Flow's `Node[]` and `Edge[]` types?

### 2. Daemon HTTP/WebSocket API
The current daemon speaks JSON-RPC over a Unix socket. The React frontend cannot open Unix sockets directly (browser security model in WebView). Two options:

**Option A: Tauri commands as bridge** — Tauri Rust layer opens the Unix socket, exposes `invoke('rpc_call', { method, params })` to the frontend. Frontend calls Tauri, Tauri calls daemon, returns result. For streaming (log lines, status updates), Tauri emits events to the frontend via `app_handle.emit()`.

**Option B: Add HTTP+WebSocket to the daemon** — `charmd` adds a localhost HTTP server (e.g. port auto-assigned per session) alongside the Unix socket. Frontend connects directly via `fetch` and `WebSocket`. The Unix socket stays for the MCP server and CLI tools.

Evaluate both. Which is simpler? Which has lower latency for log streaming? Recommend one with rationale.

### 3. Real-time graph updates
The React Flow canvas needs to update as agents are spawned, change state, and finish:
- What is the push mechanism? (WebSocket events from daemon, or Tauri event emitter)
- What events does the daemon need to emit? (`agent_spawned`, `agent_state_changed`, `gate_opened`, `gate_resolved`, `agent_log_line`, `agent_done`)
- Does the daemon currently emit these events, or does the frontend poll? (Current console polls every 1500ms — should the native app use push instead?)
- How does the frontend merge incremental events into React Flow's node/edge state without full re-renders?

### 4. Log streaming
Agent logs are streaming text (lines of Claude output, tool use results, etc.):
- How are log lines pushed to the frontend? (one WebSocket message per line? batched?)
- How is the log buffer managed in the frontend? (cap at N lines? virtualized list?)
- Which Tauri API handles this: `app_handle.emit()` per line, or a dedicated WebSocket channel per agent?

### 5. Suborchestrator / worktree context
When an orchestrator spawns a suborchestrator in a separate worktree:
- Does the suborchestrator's charm daemon run as a separate process with its own socket?
- If so, how does the parent app connect to it? (IPC between daemons, or the UI connects to both?)
- What is the data boundary between the parent graph and the suborchestrator's subgraph?

## Deliverable
A data model + integration architecture document. Write to `.charm/worktrees/native-ui/.charm/proposals/PROP-data-model-integration.md`.
