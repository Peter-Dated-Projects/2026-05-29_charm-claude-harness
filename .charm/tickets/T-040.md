## FINDINGS (investigation complete)

Full typed spec written to `.charm/kb/zed-phase-1-bridge-spec.md`. Summary below.

### The real situation

The proposal's `CharmState` (phase-1-charm-bridge.md:170-178) is mostly
aspirational. The `status` RPC at `src/daemon/index.ts:683-688` returns **exactly
three fields**, not six:

```ts
{ tickets: TicketFrontmatter[],   // frontmatter only, NO body
  agents: Agent[],                 // registry.list() verbatim
  pending_approvals: ApprovalGate[] }
```

Field-by-field gap vs. the proposal:

| Proposal field | Reality | Required daemon work |
|---|---|---|
| `tickets` | `TicketFrontmatter[]`, no body | none (read body from file if needed) |
| `agents[].parent_id` | **does not exist** -- `Agent` (schema.ts:77-91) has no parent field; no spawn path records who spawned whom | real backend work (see below) |
| `agents[].worktree` | field is `worktree_name`, and it is **always null** | rename + actually populate |
| `sub_orchestrators` | **not in status** | derive daemon-side; needs parent tracking |
| `pending_gates` | named `pending_approvals` (`ApprovalGate[]`, fully defined) | rename only |
| `coordination` | **not in status**; separate `read_coordination` RPC -> `{text}` (index.ts:934) | second poll call |
| `session` | **not in status**; only written to `meta.json`, no RPC reads it | read file directly |

### Two findings that change Phase 1 scoping

1. **The hierarchy data does not exist in the daemon.** `parent_id` /
   `sub_orchestrators` are not a serialization tweak. `registry.create()`
   (registry.ts:44-63) records no parent; every spawn path
   (`spawn_workers` index.ts:836, `spawn_investigators` :771, `request_review`
   :1315, `spawn_suborchestrator` :1294) uses `caller_id` only to authorize, never
   to link the child back. To produce the tree the daemon needs: add
   `Agent.parent_id`, thread `caller_id` into `SpawnSpec`/`spawnAgentLocked`, and
   derive `sub_orchestrators` in `status`. This is exactly the
   "backend that produces a real hierarchy is not built" gap from
   orchestration-model.md:78-80. RECOMMEND a separate daemon ticket that **blocks
   Phase 3 (canvas), not Phase 1.**

2. **`worktree_name` is always null through the MCP surface.** The
   `registry.setWorktree` plumbing fires only when `spec.cwd !== paths.root`
   (index.ts:423), but no spawn RPC passes a `cwd`. So worktree-isolated execution
   is not wired into the spawn path; `create_worktree` makes the checkout but
   nothing directs an agent into it. Populating `worktree_name` needs a
   `cwd`/worktree param on the spawn RPCs.

   The upside: **Phase 1's bridge does not need either of these.** The poll +
   apply + idle-gated inject contract is fully buildable on today's status shape;
   the hierarchy is a Phase 3 need.

### Wire protocol

- **Poll (in):** `rpc_call(socket, "status", {})` every 1500ms over the existing
  newline-delimited JSON-RPC unix socket (`rpc.ts`). Companion reads in the same
  tick: `read_coordination` -> `{text}` and a `meta.json` file read (neither is in
  `status`). Wire convention is **snake_case** (`ticket_id`, `worktree_name`,
  `pane_id`, `started_at`) -- the proposal's `parentId`/`worktree` camelCase note
  (phase-1-charm-bridge.md:257-258) is wrong. Rust client must loop on partial
  reads / drain partial writes: a status reply exceeds the ~8KB single-write
  limit (rpc.ts:7-40).
- **Inject (out) -- RECOMMENDED: bridge runs a second listen socket; daemon
  connects as a client.** There are exactly **three** `sendText`-into-an-agent-pane
  call-sites to convert: `pingOrchestrator` (index.ts:548), `continue_agent`
  (:1181), `set_mode` (:1251-1252). Replace each `tmux.sendText(paneId, text)` with
  `rpcCall(injectSock, "inject_text", {agent_id, text})`. This reuses `rpc.ts`
  wholesale on both ends and matches the existing architecture. Rejected
  alternatives: (b) server-push frame -- the current protocol is one-shot,
  id-correlated request/response with no persistent connection, so push is the
  biggest change and touches the hot path; (c) poll-marker -- up-to-1500ms latency
  on waking a blocked agent defeats the point. Daemon must no-op to the tmux path
  when no bridge is registered (legacy mode); have the bridge hand over its
  `inject.sock` path via `register_panes`/a new `register_bridge` RPC. Daemon
  addresses by `pane_id` today, bridge by `agent_id` -- daemon should send
  `agent_id` (registry already maps the two).

### apply() + callbacks + inject gating

- `apply()` overwrites tickets/agents/approvals/coordination/session and diffs the
  incoming agent-id set against the previous to fire `on_agent_spawned` for each
  new id (Option A: spawn detection rides the poll, no push channel). Pass the
  whole `&AgentRecord` (role + pane_id) to the callback; do **not** rely on
  `worktree_name` (null today). Phase 4 is the sole consumer.
- **Idle-gated inject tiers resolve from `role` + the `main-001` id, which exist
  today -- no `parent_id` needed:** `main-001` -> Orchestrator (strict idle-gate),
  `role==suborchestrator` -> Sub-orchestrator (idle-gate, looser), else Leaf
  (direct `terminal.input`).
- **Bracketed-paste risk is real and inherited.** `tmux.sendText` uses bracketed
  paste specifically because literal multi-line sends submit early on the first
  `\n` (tmux.ts:163-194). A bare `terminal.input(bytes_with_newlines)` will hit the
  same bug if claude's REPL has bracketed paste on. Prototype multi-line injection
  against a real REPL before trusting it; if it breaks, wrap in
  `ESC[200~ ... ESC[201~` + terminating Enter. A failure here is silent (agent
  never wakes).
