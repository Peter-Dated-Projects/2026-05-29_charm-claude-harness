## Goal
Go deep on GPUI specifically. It is the most production-proven GPU-accelerated Rust UI framework (powers Zed, a shipping VSCode-competitor). Assess whether charm could realistically be built on it. Use subagents to cover different angles in parallel.

## Research areas

### 1. API and programming model
- Retained mode vs immediate mode — how does GPUI model UI state?
- How do you build a resizable panel layout in GPUI? Does Zed's own panel/dock system give us a reference implementation?
- Element/Component model — how does it compare to React or Elm?
- How is async integrated? (GPUI has its own async executor)

### 2. Distribution and licensing
- GPUI is Apache 2.0 / GPL dual license as of mid-2025 — confirm current license and any restrictions for a tool built on it
- Is GPUI published as a standalone crate on crates.io, or must it be vendored from the Zed repo?
- Maintenance: is it Zed-team-only or does it accept external contributions?

### 3. Crate availability for charm's needs
- Markdown rendering (Zed uses a custom renderer — is it extractable?)
- Terminal emulator pane (Zed has a built-in terminal — is the `terminal` crate separated?)
- Tree view / file explorer widget
- Force-directed graph — any GPUI-native option or would we embed a canvas?

### 4. OTA update integration
- How does Zed itself do updates? (auto-updater, not tauri-based)
- Can that mechanism be reused or referenced?

### 5. Platform support
- macOS: native Metal backend, no WebView dependency
- Linux: Wayland/X11 support status
- Windows: support status

### 6. Real-world build experience
- Compile times for a GPUI app from scratch
- Any known pain points from developers outside the Zed team who have tried to use GPUI
- Community resources: docs quality, Discord/forum availability

## Deliverable
A 'go / no-go / conditional' verdict on GPUI as the primary framework for charm, with specific conditions listed. Write to `.charm/proposals/PROP-gpui-deepdive.md`.
