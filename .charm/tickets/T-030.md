## Findings

The diagram has been rewritten and saved to `.charm/proposals/PROP-zed-fork-build-plan/architecture-diagram.mmd`.

### Design principles extracted from apple-workflow and how each was applied

- **Dark, saturated fills + white text + bright contrasting strokes.** The old diagram used light pastel fills (`#E2E8F0`, `#D1FAE5`, `#DBEAFE`, etc.) with dark text. Every classDef is now dark and saturated with `color:#fff` and a bright accent stroke: e.g. `stay fill:#14532d,color:#fff,stroke:#4ade80,stroke-width:2px` (dark green / bright lime), `ph1 fill:#1e3a8a,color:#fff,stroke:#60a5fa,stroke-width:2px` (dark navy / bright blue). Same pattern through all 12 classes.

- **Semantic color tied to lifecycle role, one classDef per category, with a LEGEND node.** The reference maps class names directly to what a node *is* in the migration lifecycle (pd = stays, old = being eliminated, store = shared store). Applied the same idiom: `stay` = unchanged daemon, `kept` = Zed native (zero new code), `strip` = Phase 0 removals, `ph1`-`ph7` = fork phases in build order. A LEGEND node with a multi-line label explains every color and both edge styles.

- **Context-rich subgraph titles (name + path/scope + status annotation separated by `·`).** The old subgraph titles were short and plain ("Daemon Backend (unchanged)"). All titles now follow the reference pattern, e.g. `"DAEMON BACKEND · src/daemon/index.ts · unchanged · STAYS"`, `"THE BRIDGE · Phase 1 · single seam · daemon to Zed"`, `"PHASE 0 STRIP · zed upstream crates · being removed from fork"`.

- **Shape semantics: `{{hexagon}}` for entry/trigger nodes, `[rect]` for process steps.** Applied to the two user-facing entry points: `cli{{"charm CLI..."}}` (the operator's session entry) and `bridge{{"CharmBridge..."}}` (the data-ingestion entry from the daemon). All other nodes remain rects.

- **Multi-line node labels with `<br/>` and `·` separators and inline annotations.** Preserved throughout. Every node with more than one role uses `<br/>` to split lines and `·` to list sub-roles inline, e.g. `"charmd<br/>RPC · ticket store · solver · approvals"`, `"inject_text listener<br/>receives ping · continue · set_mode"`.

- **Thick `==>` for primary data flow, dashed `-.->` for secondary/control flow, all labeled.** The old diagram used plain `-->` for everything. Primary data paths (daemon status poll -> bridge -> state, state fanout to all UI surfaces, spawn_task, bootstrap sequence) now use `==>`. Control-flow paths (approve_gate, dismiss/kill, terminal.input injection, liveness teardown, hub RPC reads) now use `-.->` with labels. This distinction was missing entirely before.

- **Double-encoding via extra `style X stroke:...,stroke-width:4px` to highlight a cross-cutting set.** The reference uses pink borders to mark the "surviving API-key deploy path" on top of its classDef fills. Applied analogously: cyan (`stroke:#06b6d4,stroke-width:4px`) borders mark the primary data-flow spine (`charmd`, `bridge`, `state`, `orchestrate`, `banner`) — the five nodes that form the critical daemon-to-UI communication path. The LEGEND node itself also gets a cyan border to identify the encoding key.

- **`stroke-dasharray` on nodes representing things being removed.** Applied to the new `strip` classDef: `stroke-dasharray:5 4` gives all seven Phase 0 removal nodes (login, collab, edit-prediction, AI, remote, telemetry, auto-update) a dashed red border. This treatment was entirely absent from the original diagram, which had no Phase 0 representation at all.

### Where our diagram's meaning differs from the reference (avoided blind copying)

- **The reference's pink double-encoding marks "things that survive a migration" (the API-key path that replaces browser automation).** In our diagram, there is no analogous "some things survive, some die" split among the NEW components — every phase node is intentionally built. So the cyan border was repurposed to mean "primary data-flow spine" rather than "survivor vs. eliminated," which is the relevant cross-cutting concept in our architecture. The legend explicitly says "CYAN border = primary data-flow spine" so the semantics are self-describing.

- **The reference has a `dead` class (very dark red, thicker border) for fully-eliminated nodes distinct from `old` (dark red dashed) for nodes still present but being removed.** Our Phase 0 items are all "will be deleted from the fork" — they are not yet deleted but will be before Phase 1 begins. Using a single `strip` class (analogous to `old`) is semantically correct; there is no "dead but still running in prod" state in our context.

- **The reference diagram is `LR` (left-to-right) because its flow is linear: account management -> credential store -> deployment.** Our architecture is layered (daemon at top, bridge in the middle, UI surfaces at the bottom), so `TB` is kept. Individual subgraphs use `direction LR` where components are parallel peers (NATIVE, BOOT, APPROVE) and `direction TB` where they have a vertical data dependency (BRIDGE, TERMS, RIGHT).
