```rust
    // ...

```

**DockPosition** (`crates/workspace/src/dock.rs`):

```rust
pub enum DockPosition { Left, Bottom, Right }
```

**Panels vs Pane items**:
- Panels implement the `Panel` trait and live in the three docks (left/right/bottom sidebars). They are toggled in and out; only one is visible per dock at a time. Think: file tree, terminal panel, outline.
- Pane items implement the `Item` trait and appear as tabs in the center `PaneGroup`. Multiple can be open simultaneously in split panes. Think: editor buffers, search results.

**Pane** (`crates/workspace/src/pane.rs`, 354 KB): manages an ordered list of `Box<dyn ItemHandle>` with tab navigation, focus, drag-and-drop, history, and split operations. Adding an item:

```rust
// On Pane directly:
pane.add_item(item: Box<dyn ItemHandle>, activate_pane, focus_item, destination_index, window, cx)

// Via Workspace helpers:
workspace.add_item_to_center(item, window, cx)       // adds to last-active center pane
workspace.add_item_to_active_pane(item, None, true, window, cx)
```

**Minimal implementation**:

```rust
struct CharmView {
    focus_handle: FocusHandle,
    // state fields
}

impl EventEmitter<()> for CharmView {}

impl Focusable for CharmView {
    fn focus_handle(&self, _cx: &App) -> FocusHandle { self.focus_handle.clone() }
}

impl Item for CharmView {
    type Event = ();
    fn tab_content_text(&self, _detail: usize, _cx: &App) -> SharedString {
        "Charm".into()
    }
    // Override tab_icon, can_save, is_dirty etc. as needed
}

impl Render for CharmView {
    fn render(&mut self, _window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        div().size_full().children(/* GPUI elements */)
    }
}
```

**Entity relationship**:
- `Entity<CharmView>` is the GPUI handle (reference-counted, identity-stable).
- `impl ItemHandle for Entity<T> where T: Item` is provided by the framework — no extra work.
- `Render` is the display layer; its `render()` returns the element tree for each frame.
- `AnyView` and `AnyEntity` are type-erased variants used internally for dynamic dispatch in pane management.

### 4. GPUI element API for custom rendering

**Three-phase pipeline** (`crates/gpui/src/element.rs`):

```rust
pub trait Element: 'static + IntoElement {
    type RequestLayoutState: 'static;
    type PrepaintState: 'static;

    fn request_layout(&mut self, id, inspector_id, window, cx) -> (LayoutId, Self::RequestLayoutState);
    fn prepaint(&mut self, id, inspector_id, bounds, request_layout, window, cx) -> Self::PrepaintState;
    fn paint(&mut self, id, inspector_id, bounds, request_layout, prepaint, window, cx);
}
```

Phase 1: measure/layout (taffy). Phase 2: register hitboxes, read final bounds. Phase 3: emit draw calls to `Window`.

**Drawing primitives** — all called on `&mut Window` in `paint()` (`crates/gpui/src/window.rs`):

```
window.paint_quad(quad: PaintQuad)                              // rect with border, bg, corner radius
window.paint_path(path: Path<Pixels>, color: impl Into<Background>)  // vector path
window.paint_drop_shadows(bounds, shadows)
window.paint_inset_shadows(bounds, shadows)
window.paint_layer(bounds, f)                                   // clipping layer
window.paint_svg(bounds, svg_data, ...)                         // asset SVG icons only
window.paint_glyph(origin, font_id, glyph_id, ...)             // text
window.paint_surface(bounds, CVPixelBuffer)                     // raw pixel buffer (macOS)
```

**Bezier/path drawing** (`crates/gpui/src/path_builder.rs`, wraps the Lyon tessellation library):

```rust
let mut builder = PathBuilder::stroke(px(2.0));   // or PathBuilder::fill()
builder.move_to(point(px(10.), px(10.)));
builder.line_to(point(px(100.), px(50.)));
builder.curve_to(control_pt, end_pt);              // quadratic bezier (= SVG Q)
builder.cubic_bezier_to(c1, c2, end_pt);           // cubic bezier (= SVG C)
builder.arc_to(radii, angle, flags, end_pt);       // elliptical arc (= SVG A)
builder.add_polygon(points);
builder.translate(vec2(dx, dy));
builder.rotate(degrees);
let path: Path<Pixels> = builder.build();
window.paint_path(path, gpui::black());
```

This is the full SVG `<path>` analogue. Covers everything needed for the ticket graph (nodes, edges, bezier routing, arrowheads).

**Animation** (`crates/gpui/src/window.rs:2182`):

```rust
// Continuous animation — call from Element::paint() to drive the next frame:
window.request_animation_frame();   // notifies current view on next vsync frame

// One-shot post-frame callback:
window.on_next_frame(|window, cx| { ... });
```

`request_animation_frame()` is the direct analogue of the web's `requestAnimationFrame`. For traveling-dot animation: store a `t: f32` in the view, increment it in `prepaint` or `paint`, call `window.request_animation_frame()` at the end of `paint()`, and GPUI will schedule the next redraw.

**SVG embedding**: No. `window.paint_svg()` renders pre-loaded asset SVGs only (loaded via `Asset` trait at startup into a GPU atlas). It does not accept arbitrary SVG strings or file paths at runtime.

**HTML embedding**: No. GPUI has no HTML renderer. Confirmed: zero matches for HTML/DOM embedding anywhere in the codebase.

**WebView / WKWebView**: No. Searched the full zed repo for `WKWebView`, `WebView`, `webview`, `WebviewView` — zero results. GPUI is a native GPU renderer (Metal/Vulkan) and deliberately does not expose a browser component. The `paint_surface(CVPixelBuffer)` API exists for embedding raw pixel data (e.g., a Metal-rendered layer) but is not a WebView.

**Implication for charm**: The traveling-dot animation from the current SVG dashboard must be fully re-implemented using `PathBuilder` + `request_animation_frame`. This is entirely doable but is custom work — no SVG passthrough is available.

`TerminalPanel` itself holds `active_pane: Entity<Pane>` and `center: PaneGroup` — it's a self-contained pane group, not a single terminal. Multiple terminal instances are just items in that internal pane.

### 6. Inter-component communication

**Three mechanisms**:

1. **Actions** (`crates/gpui/src/action.rs`): Global or window-scoped commands. Defined with `actions!(module, [MyAction])`, dispatched with `cx.dispatch_action(Box::new(MyAction))`. Used for keyboard shortcuts, menu items. One-way fire-and-forget.

2. **Events** (`EventEmitter<E>`): Point-to-point typed events. Emit: `cx.emit(MyEvent::TicketUpdated(id))`. Subscribe: `cx.subscribe(&entity, |this, emitter, event, cx| { ... })`. Subscriber gets a strong `Entity<T>` reference. Good for peer-to-peer state propagation.

3. **Notify** (`cx.notify()`): Marks a view dirty — no data, just "re-render this". The rendering system re-calls `render()` on next frame. Used for pure visual refresh after state was already mutated.

**Pattern for Unix socket → UI** (the charm daemon integration):

```rust
// In CharmPanel::new():
let (tx, mut rx) = futures::channel::mpsc::channel::<DaemonUpdate>(64);

// spawn_daemon_reader connects tx to the Unix socket reader
let _socket_task = cx.spawn(cx, async move |this, mut cx| {
    while let Some(update) = rx.next().await {
        this.update(&mut cx, |panel, cx| {
            panel.apply_update(update);
            cx.notify();           // triggers re-render
        }).ok();
    }
});
_socket_task.detach();
```

The Unix socket reader runs in a background async task (spawned with `cx.spawn` or Tokio). On each message it calls `cx.notify()` through the entity handle. GPUI's async executor bridges the background thread to the UI thread safely — this is the exact pattern used throughout Zed for LSP and project watcher state changes.

For richer cross-component updates (e.g., terminal panel reacting to orchestrator events), use `cx.emit(CharmEvent::AgentStatusChanged { ticket_id, status })` from the background task handler, and have dependent views subscribe.

### Summary for implementation

- **CharmPanel** (ticket graph sidebar): implement `Panel` (10 required methods) + `Focusable` + `EventEmitter<PanelEvent>` + `Render`. Register via `workspace.add_panel()`. Left or right dock.
- **CharmView** (center canvas): implement `Item` + `Focusable` + `EventEmitter` + `Render`. Add via `workspace.add_item_to_center()`.
- **Custom rendering**: use `PathBuilder` (Lyon) for all graph geometry; `window.request_animation_frame()` for animation. No SVG/HTML/WebView option.
- **Terminal spawning**: `terminal_panel.spawn_task(&SpawnInTerminal { command, args, env, cwd, ... })` — this is the exact API for `charm start` agent spawning.
- **Daemon updates**: `cx.spawn()` background task + `cx.notify()` on data arrival is the canonical GPUI async bridge.
