We are forking the Zed editor (https://github.com/zed-industries/zed) for internal use only. GPL-3.0 is not a concern. Research and document everything needed to go from zero to a working fork.

1. **Fork and build from source**: What are the exact steps to fork zed-industries/zed, clone locally, and get a clean build on macOS (primary target)? What Rust toolchain version does Zed currently require? Any special toolchain components (rust-src, wasm32 targets, etc.)? What is the actual first-build time on Apple Silicon?

2. **Feature stripping**: Zed has features we will never use: collaborative editing (CRDTs, real-time multiplayer), Zed AI / LLM assistant panel, remote development (SSH), Zed account / telemetry, auto-update (we'll manage our own distribution). For each, identify:
   - Which crates own the feature
   - Whether it can be disabled via Cargo feature flags or requires code deletion
   - Any compile-time savings from removing it
   - Any runtime/binary-size savings

3. **Crate map**: Produce a map of the ~20-30 most important crates in the Zed monorepo relevant to our use case: `gpui`, `workspace`, `pane`, `terminal`, `terminal_view`, `editor`, `project`, `fs`, `settings`, `theme`, `ui`, `ui_input`, `language`, `command_palette_ui`. For each: one-line purpose, key public types/traits, and whether charm will use it as-is, modify it, or ignore it.

4. **Build configuration**: Is there a dev vs release profile worth knowing about? Any build scripts that fetch remote assets (model weights, fonts, etc.) we need to stub? Any code-signing or entitlement requirements on macOS that would block a dev build?

5. **CI baseline**: What does a minimal GitHub Actions / CI setup look like for a Zed fork? What does Zed's own CI do that we should replicate vs skip?

6. **Public fork examples**: Are there any public GitHub repos that fork or significantly customize Zed's internals (not just themes/extensions)? What did they do?

Write concrete findings with specific file paths, crate names, and commands.

## Findings

### 1. Fork and Build from Source

**Fork steps:**
```
gh repo fork zed-industries/zed --clone --remote
cd zed
```

**Rust toolchain** (pinned in `rust-toolchain.toml`):
- Channel: `1.95.0`
- Profile: `minimal`
- Components: `rustfmt`, `clippy`, `rust-analyzer`, `rust-src`
- Targets: `wasm32-wasip2` (extensions), `wasm32-unknown-unknown` (GPUI web), `x86_64-unknown-linux-musl` (remote server)

rustup handles all of this automatically when you run any cargo command inside the repo.

**macOS build prerequisites:**
```
xcode-select --install
sudo xcode-select --switch /Applications/Xcode.app/Contents/Developer
sudo xcodebuild -license accept
brew install cmake
```

**Build commands:**
```
cargo run               # debug build, fastest iteration
cargo run --release     # release build, slower compile
cargo test --workspace  # full test suite
```

**First-build times on Apple Silicon (reported by community, debug builds):**
- M2 Max: ~3 min 18 s
- M3 MacBook Air on wall power: ~25 min; on battery: ~40 min (power throttle)
- M4 Max: ~3 min

The M3 Air outlier is power management, not chip capability. M3 Pro/Max should be in the 3-5 min range. `sccache` + `CARGO_INCREMENTAL=0` can cut subsequent builds significantly.

### 2. Feature Stripping

**Critical finding: there are no compile-time Cargo feature flags to disable any of these features.** They are unconditional workspace crates depended on by `crates/zed/Cargo.toml`. Feature stripping requires removing crates from the workspace and deleting their call sites in `crates/zed/src/main.rs` (and related init code). There is no `--no-default-features` path.

This is confirmed by the Gram fork (see section 6), which deleted crates wholesale.

#### Collaborative editing (CRDTs, real-time multiplayer)

Crates to delete:
- `crates/collab` -- NOTE: this is the server-side collab daemon binary, not the client; it runs at collab.zed.dev. Low priority to strip vs the client-side crates below.
- `crates/collab_ui` -- client-side collaboration UI (join/host session panels)
- `crates/call` -- LiveKit-based audio/video calling during collab sessions; depends on `livekit_client`
- `crates/channel` -- Zed text chat channels

`crates/rpc` is the shared protocol layer; it can be kept as it is also used by `remote`.

**Compile savings:** LiveKit and WebRTC deps are large. `call` pulls in `livekit_client` which vendors WebRTC native libraries (~50-100 MB of native code). This is the biggest binary-size win.

#### Zed AI / LLM assistant panel

Crates to delete:
- `crates/agent` -- conversational coding agent
- `crates/agent_servers` -- external agent server connections
- `crates/agent_settings` -- agent settings structs
- `crates/agent_skills` -- agent skill definitions
- `crates/agent_ui` -- AgentPanel UI
- `crates/anthropic` -- Anthropic API client
- `crates/bedrock` -- AWS Bedrock API client
- `crates/language_model` -- LLM provider abstraction trait
- `crates/language_model_core` -- core LLM types
- `crates/language_models` -- built-in provider implementations
- `crates/language_models_cloud` -- Zed cloud LLM proxy
- `crates/copilot` -- GitHub Copilot integration
- `crates/copilot_chat` -- Copilot Chat
- `crates/copilot_ui` -- Copilot UI panels

**Compile savings:** large; these crates pull in reqwest, HTTP/async clients, JSON serialization for many schemas. Rough estimate: 20-30% of total non-GPUI compile time.

#### Remote development (SSH)

Crates to delete:
- `crates/remote_server` -- daemon binary that runs on the remote host; separate binary, not linked into main zed
- `crates/remote_connection` -- connection management
- `crates/remote` -- client-side remote project type

`crates/remote` IS a direct dep of the main `zed` crate (`remote.workspace = true` in `crates/zed/Cargo.toml`). Removing it requires deleting the `RemoteConnectionOptions` / `open_remote_project` call sites in `crates/zed/src/main.rs`.

**Compile savings:** moderate; main savings is not building the `remote_server` binary at all.

#### Zed account / telemetry

Crates to delete:
- `crates/telemetry` -- event collection and dispatch
- `crates/telemetry_events` -- event type definitions
- `crates/oauth_callback_server` -- OAuth for Zed account login

`crates/client` handles Zed Cloud WebSocket connections and is also used by `collab_ui` and `remote`. If you strip all three collaboration/remote/AI cloud features, `client` can also be removed or gutted. If any cloud feature remains, keep `client` but stub out the telemetry registration call in `crates/zed/src/main.rs`.

**Runtime savings:** eliminates outbound HTTP calls on startup.

#### Auto-update

Crates to delete:
- `crates/auto_update` -- update check + download logic
- `crates/auto_update_helper` -- privilege escalation helper for applying updates
- `crates/auto_update_ui` -- update nag UI

**Compile savings:** minor; these crates are small.

### 4. Build Configuration

**Debug vs release:**
- `cargo run` (debug): fast recompile (~10-30s incremental on M2), unoptimized, includes debug symbols. Use for development.
- `cargo run --release`: full optimization, much slower first build. Only needed for distribution testing.
- Zed defines a `release-fast` profile (in `Cargo.toml`) with LTO disabled for faster release-like builds.

**Build scripts that fetch remote assets:**
- `script/bundle-mac` downloads `dugite-native` (a bundled git binary from github.com/desktop/dugite-native) at bundle time, NOT at compile time. This only runs when building a distributable .app bundle, not for `cargo run`.
- No model weights, fonts, or other remote assets are fetched during `cargo build` / `cargo run`.
- Fonts are embedded directly in `crates/assets/` as binary data.

**Code signing on macOS:**
- `cargo run` in dev mode does NOT require code signing. The binary runs directly.
- Code signing (`crates/zed/resources/zed.entitlements`) is only required by `script/bundle-mac` for a distributable `.app` bundle.
- Entitlements include: `com.apple.security.network.client` (outbound network), `com.apple.security.files.user-selected.read-write` (file access), and screen capture / accessibility permissions. A fork can modify or reduce these.
- On macOS 15+, running an unsigned dev build may trigger Gatekeeper warnings but will not block execution in dev.

**MACOSX_DEPLOYMENT_TARGET:** Set to `10.15.7` (Catalina) in `crates/zed/build.rs`. The build.rs also weakly links ReplayKit and ScreenCaptureKit for backward compat; no action needed for a fork.

### 5. CI Baseline

**What Zed's CI does** (from `.github/workflows/run_tests.yml`, generated by `cargo xtask workflows`):

| Job | Runs on | What it does |
|---|---|---|
| `orchestrate` | Ubuntu | Computes changed-package filterset via `cargo metadata` + `git diff` |
| `check_style` | Ubuntu 22.04 | `rustfmt --check`, `cargo check` |
| `clippy_linux` | Ubuntu 22.04 (16-core) | `cargo clippy --workspace` |
| `clippy_mac` | macOS large | `cargo clippy` |
| `clippy_mac_x86_64` | macOS large | `cargo clippy --target x86_64-apple-darwin` |
| `clippy_windows` | Windows 32-core | `clippy.ps1` |
| `test_linux` | Ubuntu 22.04 (16-core) | `cargo nextest run --workspace` |
| `test_mac` | macOS large | `cargo nextest run --workspace` |
| `test_windows` | Windows 32-core | `cargo nextest run --workspace` |
| `check_licenses` | Ubuntu | script/check-licenses |
| `check_docs` | Ubuntu | docs build check |
| `run_action_checks` | Ubuntu | actionlint on workflow files |

Change-based filtering: on PRs, only re-tests `rdeps(changed_package)` -- skips the full suite if only one crate changed.

**Minimal CI for a charm fork:**

```yaml
on:
  pull_request:
  push:
    branches: [main]

jobs:
  check:
    runs-on: macos-latest   # or a self-hosted Apple Silicon runner
    steps:
      - uses: actions/checkout@v4
      - name: install rust
        run: rustup show   # picks up rust-toolchain.toml automatically
      - name: clippy
        run: cargo clippy --workspace -- -D warnings
      - name: test
        run: cargo nextest run --workspace --no-fail-fast
```

**Skip from Zed's CI:**
- Windows and Linux jobs (macOS-only fork)
- `clippy_mac_x86_64` cross-compile job (unless x86 support needed)
- License check (unless distributing publicly)
- `bump_collab_staging` / deploy workflows (cloud infra)
- `community_*` workflows (issue triage bots)

**Tools used by Zed CI worth adopting:**
- `cargo nextest` (faster parallel test runner, replaces `cargo test`)
- `namespace-profile` runners (Zed uses Namespace for cache-aware Linux runners; for a fork, standard GitHub Actions runners work fine)

### 6. Public Fork Examples

**Gram** (`codeberg.org/GramEditor/gram`, mirror at `github.com/GramEditor/gram`):
- Created March 2026 by Kristoffer Gronlund
- Removed: all AI/LLM (agent, agent_ui, anthropic, bedrock, language_model*, copilot*), telemetry, auto-update, collaboration, account/auth
- Approach: direct code deletion -- removed crate workspace members from root `Cargo.toml` and deleted their call sites. Confirmed by diffing Gram's Cargo.toml against Zed's: `agent`, `agent_servers`, `agent_settings`, `agent_skills`, `agent_ui`, `anthropic`, `bedrock`, `auto_update`, `auto_update_helper`, `auto_update_ui`, `call`, `channel`, `collab_ui`, `copilot`, `copilot_chat`, `copilot_ui`, `language_model`, `language_model_core`, `language_models`, `language_models_cloud`, `oauth_callback_server`, `telemetry`, `telemetry_events` are all absent from Gram's workspace.
- Renamed `crates/zed` to `crates/gram` (main binary crate)
- Actively tracks Zed main; upstreams bug fixes back

**Zedless** (`github.com/zedless-editor/zedless`):
- Privacy-focused, local-first fork
- Approach: AST-level patching via `ast-grep` (tree-sitter based) rather than maintaining a full fork. Generates patch scripts, not a persistent forked codebase. Better for tracking upstream rapidly, harder to reason about.
- Removed: telemetry, cloud providers, auto crash reporting

**Rainlab dev fork** (`github.com/rainlab-inc/zed-dev`):
- Internal dev fork; minimal public documentation on what changed

**Recommendation for charm:** follow Gram's approach (code deletion, not patching). The patch-script approach (Zedless) is clever for minimizing diff but creates a fragile pipeline that can break on upstream refactors. A direct fork with clean deletion is easier to own and debug.

### What a worker will need

**Entry points for the strip work:**
- `crates/zed/Cargo.toml` -- remove the unwanted crates as direct deps
- `Cargo.toml` (root) -- remove the crates from `[workspace.members]` and `[workspace.dependencies]`
- `crates/zed/src/main.rs` -- delete `use` imports and initialization calls for each stripped crate (search for `agent::`, `collab_ui::`, `auto_update::`, `telemetry::`, `remote::`, `call::`, `channel::` etc.)
- `crates/zed/src/zed.rs` (if it exists) -- secondary init file; check for feature registrations

**Files a build ticket should touch:**
- `Cargo.toml` (root workspace)
- `crates/zed/Cargo.toml`
- `crates/zed/src/main.rs`
- Possibly `crates/zed/src/zed.rs`, `crates/title_bar/` (collab participant display), `crates/notifications/` (collab notifications)

**Edge cases and gotchas:**
1. `crates/text` uses CRDTs internally -- do NOT try to remove it. The CRDT model is the buffer. Collaboration network sync is in `collab_ui`/`call`/`channel`.
2. `crates/client` is tangled: it handles both the Zed Cloud collab connection AND the LLM token refresh (`RefreshLlmTokenListener`). After stripping AI and collab, audit whether `client` can be removed entirely or just gutted. If `remote` is also stripped, `client` becomes vestigial.
3. `crates/collab` is the server-side daemon binary (runs on collab.zed.dev), not a client crate. It depends on PostgreSQL and AWS SDKs. Leave it in the workspace (it's harmless to keep as a workspace member even if unused) or delete the directory; it won't be linked into the main binary either way.
4. wasm32 targets are needed only for extension support. If charm will not support user-installable extensions, the `wasm32-wasip2` and `wasm32-unknown-unknown` targets can be removed from `rust-toolchain.toml`, saving toolchain download time.
5. `x86_64-unknown-linux-musl` target in `rust-toolchain.toml` is for building the `remote_server` binary for deployment on Linux remote hosts. Remove it if stripping remote dev.
6. The Namespace runner caching in Zed's CI workflows uses `namespacelabs/nscloud-cache-action` -- this won't work on standard GitHub Actions runners. Replace with `actions/cache` for `~/.cargo` and `target/`.
7. First build cold-cache in CI is expensive (~15-25 min on a standard GitHub macOS runner). Use `sccache` with a remote cache (S3 or GitHub Cache) or self-hosted Apple Silicon runners to get this down.
