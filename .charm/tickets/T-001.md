## Background

This is the first of three source files in a minimal string-utils library used as
a harness self-test. The function is intentionally trivial; the goal is to
exercise the charm pipeline (ticket creation, review, testing, gate) rather than
produce production-quality code.

## Task

Create `src/upper.js` exporting a single named function `upper(s)` that returns
`s.toUpperCase()`. No external dependencies. The file must export exactly one
function.

## Acceptance criteria

- [ ] `src/upper.js` exists at the repo root under `src/`.
- [ ] The file uses a named export: `export function upper(s)` (ESM) OR
      `module.exports = { upper }` (CJS) — either form is acceptable as long as
      it is importable by name from `cli.js`.
- [ ] `upper("hello")` returns `"HELLO"`.
- [ ] `upper("Hello World")` returns `"HELLO WORLD"`.
- [ ] No `import` / `require` statements — zero external dependencies.
- [ ] No other exported symbols are present in the file.

## Edge cases and failure modes

- **Non-string input**: `s.toUpperCase()` will throw a TypeError if `s` is not a
  string (e.g. `null`, `undefined`, a number). Per project non-goals, error
  handling is explicitly out of scope — do not add guards.
- **Empty string**: `upper("")` must return `""` without error; the native method
  handles this correctly.
- **Already-uppercase input**: `upper("ABC")` must return `"ABC"` — idempotent,
  no special casing needed.
- **Module format mismatch**: if `cli.js` uses `import` (ESM) but `upper.js` uses
  `module.exports` (CJS) without a `"type": "module"` field in `package.json`,
  the import will fail at runtime. The worker should check (or create) a
  `package.json` that is consistent with whichever module format they choose.
- **Multiple exports**: adding helper functions or a default export would violate
  the "exactly one named function" constraint checked by the tester.

## Notes

`touches` is already narrowed to `src/upper.js` — no other files should be
modified by this ticket. If a `package.json` needs to be created or updated to
align module formats, that is out of scope here and should be handled by the
`cli.js` ticket (T-003 / T-C) which owns the integration layer.
