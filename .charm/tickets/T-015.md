## Goal
Investigate whether a spatial, canvas-based UI (like Obsidian's canvas view or Miro) is feasible in Rust, what it would look like for charm, and which frameworks best support it. Spawn subagents to research the rendering requirements and prior art in parallel.

## What 'spatial UI' means for charm
Instead of a fixed tab layout, agents/tickets/KB nodes float as cards on an infinite canvas. The operator can:
- Pan and zoom the canvas
- See ticket dependency edges as drawn arrows
- Drag tickets to spatial positions
- Expand a ticket card to see its plan/log inline
- The force-directed KB graph from `charm-graph` is embedded directly on canvas
- Real-time streaming agent output visible in-place as cards update

## Research questions
1. Which Rust frameworks have primitives for infinite canvas / pan-zoom? (egui has this via `egui::Area` + transform; GPUI has explicit 2D transforms; Dioxus has no built-in canvas but can embed a WebGL canvas)
2. What crates exist for force-directed graph layout in Rust? (`fdg-sim`? `petgraph`? custom?)
3. What is the implementation cost of a pan-zoom infinite canvas in each top framework vs building on a web canvas (via Tauri/Dioxus web)?
4. Prior art: how did Obsidian build their canvas? (Electron + custom Canvas2D renderer) — what are the lessons?
5. How does spatial UI interact with the approval workflow? (modal-style overlay on canvas vs separate pane?)
6. Performance ceiling: how many agent cards + edges can a Rust canvas render at 60fps?

## Deliverable
A feasibility verdict (build vs skip), estimated effort, and framework recommendation for spatial UI. Write to `.charm/proposals/PROP-spatial-ui-feasibility.md`.
