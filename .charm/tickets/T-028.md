Given we are forking Zed for internal use, map every charm harness component to its Zed-native equivalent, and identify what new code must be written. Use findings from T-024 (the TerminalBackend analysis, already in .charm/tickets/T-024.md) as the component inventory.

For each component, answer: does Zed provide this natively, do we modify Zed's existing code, or do we write a new GPUI component?

1. **tmux pane grid -> Zed pane layout**: charm's daemon manages a tmux grid (console left, orchestrator center, sub-agents in a 2-row grid right). Zed has a workspace with configurable pane splits. How would we replicate the charm layout in Zed? Is it possible to programmatically open pane splits in a specific arrangement at session start? Or does Zed's layout need to be user-driven?

2. **charm-console (Ink TUI) -> Zed panel**: The charm console has four tabs: Artifacts (file/ticket browser + markdown preview), Approvals (pending gates), Agents (fleet status), Files (project tree). Each maps to a Zed dock panel. What is the implementation strategy for each tab as a GPUI panel?

3. **Orchestration canvas -> Zed pane item**: The hero is the animated node graph (orchestrator squares, agent circles, worktree dashed boxes, traveling dots on edges). This must be a center-area pane item. Given GPUI's GPU-native rendering (no SVG, no animateMotion), what is the GPUI implementation strategy for the animated graph? Be specific about: the Element implementation, how to drive the dot animation, how to handle click events on nodes.

4. **Per-agent terminal tabs -> Zed terminal_view**: charm currently spawns each claude agent in its own tmux pane. In a Zed fork, each agent gets its own terminal tab in the center pane area (or a dedicated agents panel). Is there a Zed API to programmatically spawn a terminal with a specific command, env vars (CHARM_SOCKET, CHARM_AGENT_ID), and working directory? Find the exact call.

5. **pingOrchestrator + continue_agent (text injection) -> Zed terminal input**: The daemon injects text into a running claude PTY to wake the orchestrator and unblock agents. In tmux this is `paste-buffer`. In a Zed fork with `terminal_view`, how would you write text to a specific terminal's PTY input programmatically from the daemon or from a GPUI action?

6. **charm start / session bootstrap -> Zed workspace open**: When `charm start` is called today it creates a tmux session and lays out panes. In a Zed fork, what replaces this? A custom `charm start` that launches the Zed fork (our binary) with a specific workspace + session UUID? Or does the user just open the IDE and it detects the .charm/ directory?

7. **Orchestrator Hub (multi-session switcher) -> Zed**: The Hub is currently a separate Tauri WebviewWindow. In Zed, what would be the equivalent? A modal? A separate window (does GPUI support multiple top-level windows)?

8. **Approval gates UX**: The approval gates (Stage 2: approve worker plan, Stage 4: approve diff before merge) need a prominent blocking UI element. What Zed UI pattern fits best — a modal dialog, a notification banner, a dedicated panel section?

Write a complete mapping table and implementation strategy. Identify the top 3 risks or unknowns that need a prototype to resolve.

### 1. tmux pane grid -> Zed pane layout

**What Zed provides:** `Workspace` manages a `PaneGroup` tree. Each `Pane` is a tab container. The workspace supports programmatic splits: `workspace.split_and_clone(pane, SplitDirection::Right, cx)` or `workspace.open_item_by_id()` into a specific pane. Left/right/bottom dock panels are separate from the center pane area.

**Charm layout:** console left dock, orchestration canvas in center pane, per-agent terminal tabs in a right-side pane split (or as tabs in the same center pane), a horizontal split for the orchestrator terminal.

**Is programmatic layout at session start possible?** Yes. In the Zed fork's session-init path (runs when a `.charm/` directory is detected), dispatch a sequence of GPUI actions:
1. Open the left dock at `DockPosition::Left` with the `CharmConsolePanel`
2. In the center `Pane`, add the `CharmCanvasItem`
3. Split the center pane right (`SplitDirection::Right`) to create an agents pane
4. Add agent `TerminalView` items into the agents pane as they spawn

**Dynamic relayout (agents spawn/die):** Zed does not have a bulk `apply_layout` API like tmux. Each pane item add/close must be done individually. The daemon fires `spawnAgentLocked` -> Zed fork receives `agent_spawned` notification -> opens a new `TerminalView` in the agents pane. When `tearDownAgent` fires -> close that `TerminalView` item. No relayout math needed — Zed's `PaneGroup` handles sizing automatically. The `layout.ts` checksum calculation disappears entirely.

**Verdict:** Zed's pane system is sufficient. The dynamic grid is simpler than tmux because Zed handles sizing without charm computing a custom-layout string. New code: a `session_init.rs` module in the fork that fires the initial pane arrangement on `.charm/` detection, and an agent-lifecycle listener that adds/removes terminal items.

### 2. charm-console (Ink TUI) -> Zed panel

Each tab becomes one or more GPUI panel implementations.

**Artifacts tab (file/ticket browser + markdown preview):**
- Implement `Panel` trait on `ArtifactsPanel { state: Entity<ArtifactsState> }`
- `ArtifactsState` holds the file list (polled from daemon `status` RPC + chokidar-equivalent file-watching via `cx.background_executor().spawn(async { notify::watch(...) })`)
- File list rendered as a GPUI `List` element; clicking a file updates `selected_file`
- Markdown preview: Zed's `markdown` crate ships `MarkdownElement` — use it directly, zero from-scratch work
- Daemon polling: `cx.background_executor().spawn(periodic_rpc_poll(socket_path, "status"))` pushing updates via `cx.notify()`

**Approvals tab:**
- `ApprovalsPanel { state: Entity<ApprovalsState> }` where `ApprovalsState` holds `Vec<PendingGate>`
- Each gate rendered with label, stage badge, and Approve/Reject buttons
- Button click fires `approve_gate` RPC on the socket
- Also triggers the modal (see item 8)

**Agents tab:**
- `AgentsPanel` rendering a list of `AgentRow { id, role, status, pane_handle }` with Dismiss (`dismiss_agent` RPC) and Kill (`kill_agent` RPC) actions
- Kill needs a double-confirm (same semantics as the Ink `x·x` double-key — use a `pending_kill: Option<AgentId>` state with a timer reset)

**Files tab:**
- Use Zed's existing `ProjectPanel` as-is. Register it normally via `ProjectPanel::init(cx)`. Zero new code.
- The Ink console's Files tab is fully superseded by Zed's native file tree.

All four panels share the same daemon-socket polling pattern as the Ink console's `useStatus` hook. The 1500ms poll becomes a background task that calls the daemon `status` RPC and calls `entity.update(cx, |state, cx| { state.update_from_status(response); cx.notify(); })`.

### 3. Orchestration canvas -> Zed pane item

**GPUI has no SVG renderer and no `animateMotion`.** The Tauri design's animated SVG canvas must be redrawn entirely using GPUI's GPU-native element API. This is the largest single build item.

**Element implementation:**

```rust
struct CharmCanvasElement {
    state: Entity<CanvasState>,
}

impl Element for CharmCanvasElement {
    type RequestLayoutState = ();
    type PrepareState = ();

    fn paint(&mut self, bounds: Bounds<Pixels>, _: &mut (), cx: &mut WindowContext) {
        let state = self.state.read(cx);
        // Paint edges as bezier paths
        for edge in &state.edges {
            cx.paint_path(edge.bezier_path(), fill(edge_color));
        }
        // Paint node boxes (orchestrators = squares, agents = circles)
        for node in &state.nodes {
            cx.paint_quad(node.bounds(), corner_radii(node), fill(node.color()));
            cx.paint_text(node.label(), node.label_bounds(), text_style());
        }
        // Paint traveling dots
        for dot in &state.animation.dots {
            cx.paint_quad(dot.bounds(), CornerRadii::full(), fill(dot_color));
        }
        // Request next frame if any animation is active
        if state.animation.is_active() {
            cx.request_animation_frame();
        }
    }
}
```

**Driving the dot animation:**

`cx.request_animation_frame()` schedules the window to repaint on the next vsync (typically 60fps). The animation loop:
1. When a new edge-traversal event arrives (agent spawned, RPC in flight), push a `TravelingDot { edge_id, t: 0.0, started_at: Instant::now() }` into `state.animation.dots`
2. In `paint()`, before painting dots, advance each dot's `t` based on `elapsed / duration`; remove dots where `t >= 1.0`
3. Call `cx.request_animation_frame()` at the end of `paint()` whenever any dot has `t < 1.0`
4. The next vsync fires `render()` -> `paint()` again; this loop self-terminates when no dots remain

This is the standard GPUI animation pattern used by Zed's own cursor blink animation and completion menu fade.

**Click events on nodes:**

In `paint()`, register a mouse-down handler per node using the hit-region API:
```rust
cx.on_mouse_event(move |event: &MouseDownEvent, phase, cx| {
    if phase == DispatchPhase::Bubble && node_bounds.contains(event.position) {
        cx.dispatch_action(Box::new(OpenNodeDetail { node_id }));
    }
});
```
The `node_bounds` are computed during layout from the current `CanvasState` positions. Node positions are managed by a force-directed layout algorithm (see item 3 risk below).

**CharmCanvasItem (the pane item wrapper):**
Implement `Item` trait on `CharmCanvasItem` (which renders `CharmCanvasElement`). `Item` requires: `tab_content()`, `tab_tooltip_text()`, `is_singleton()` (return true — only one canvas per session). Register with the workspace item registry so it can be opened via `workspace.open_item()`.

### 4. Per-agent terminal tabs -> Zed terminal_view

**Zed provides this natively.** The exact call path in a Zed fork:

```rust
// In the charm agent spawn handler (called after spawnAgentLocked fires via daemon socket):
fn spawn_agent_terminal(
    agent: &AgentRecord,
    workspace: WeakView<Workspace>,
    cx: &mut AppContext,
) {
    let cmd = spawn_ts_equivalent_command(agent); // same string as spawn.ts builds today
    let cwd = PathBuf::from(&agent.cwd);

    workspace.update(cx, |workspace, cx| {
        let project = workspace.project().clone();
        let terminal = project.update(cx, |project, cx| {
            project.create_terminal(
                TerminalKind::Shell(Some(cwd)),  // or TerminalKind::Task for command override
                workspace.window_handle(),
                cx,
            )
        });

        // Inject env vars after creation — Terminal exposes set_env or accepts env at spawn
        terminal.update(cx, |term, _cx| {
            term.set_initial_command(Some(cmd));
            // CHARM_SOCKET and CHARM_AGENT_ID are set via TerminalSettings env override,
            // or by prepending `export CHARM_SOCKET=...; export CHARM_AGENT_ID=...;` to cmd
        });

        let terminal_view = cx.new_view(|cx| {
            TerminalView::new(terminal, workspace.weak_handle(), cx.focus_handle(), cx)
        });

        // Add to the agents pane (not the center pane where the canvas lives)
        let agents_pane = workspace.charm_agents_pane(); // custom handle tracked at session init
        agents_pane.update(cx, |pane, cx| {
            pane.add_item(Box::new(terminal_view), true, true, None, cx);
        });
    });
}
```

The most robust env-var injection: prepend `export CHARM_SOCKET=<path>; export CHARM_AGENT_ID=<id>;` to the command string before passing to `TerminalKind::Shell`. This matches what `spawn.ts` does today and requires no Zed API changes.

**Liveness detection:** Replace `sweepDeadPanes` (polls `tmux list-panes --pane_dead`). In a Zed fork, `Terminal` fires a `TerminalEvent::CloseTerminal` event when the underlying process exits. Subscribe to this in the `CharmSessionManager`:
```rust
cx.subscribe(&terminal, |_, event, cx| {
    if let TerminalEvent::CloseTerminal = event {
        // Fire equivalent of tearDownAgent
        charm_daemon_socket.send_rpc("agent_exited", ...);
    }
});
```
This is event-driven rather than poll-based — cleaner than the current 15s sweep.

### 5. pingOrchestrator + continue_agent -> Zed terminal input

**Root problem:** The charm daemon is a separate process. It cannot call Rust methods on Zed's in-process `Terminal` entity directly. The PTY write must be bridged.

**Solution: add a PTY injection IPC endpoint to the Zed fork.**

The Zed fork's `CharmSessionManager` opens a Unix socket listener (a second socket, separate from charmd's socket — call it the "IDE bridge socket"). The daemon sends a new `inject_text` RPC to this socket with `{ agent_id, text }`. The session manager looks up the `Terminal` entity for that agent and calls:

```rust
terminal.update(cx, |terminal, _cx| {
    // Terminal::input() is the user-keystroke entry point; it writes bytes to the PTY master.
    // This is exactly how Zed's own keyboard handler works internally.
    terminal.input(text.into_bytes());
});
```

The `Terminal::input()` method is in `crates/terminal/src/terminal.rs`. It sends to `self.pty_tx` (an `UnboundedSender<Bytes>` that writes to the PTY master fd). This handles multi-line text correctly because it writes raw bytes — no Enter-key-simulation needed. Bracketed paste mode is handled by prepending `\x1b[200~` and appending `\x1b[201~` if the terminal has bracketed paste enabled.

**What must be added to the Zed fork:**
- `charm_bridge_socket.rs`: small Unix socket listener that receives `inject_text` RPCs
- A registry: `agent_id -> WeakView<Terminal>` maintained by `CharmSessionManager`
- The daemon's `pingOrchestrator` and `continue_agent` handlers call the new bridge socket instead of `tmux.sendText()`

The daemon-side change is minimal: replace `tmux.sendText(paneId, text)` with `bridgeSocket.sendRpc("inject_text", { agent_id, text })` in `src/daemon/index.ts`.

### 6. charm start / session bootstrap -> Zed workspace open

**Recommended approach: `charm-zed <project-path>` launch command with auto-init.**

```
charm start                     # today: tmux session + daemon + panes
charm-zed /path/to/project      # Zed fork: opens IDE + starts daemon + auto-configures layout
```

On binary launch with a project path argument:
1. Check for `.charm/` directory (same as `charm init` check today)
2. Start charmd daemon if not already running (same logic as `charm start` today, minus the tmux calls)
3. Wait for daemon socket to appear (same `waitForSocket` logic)
4. Open the Zed workspace at that path
5. After workspace is ready, the `CharmSessionManager` (activated by `.charm/` detection) calls the init sequence: open left dock panels, open canvas pane item, split right pane for agents
6. Call `register_panes` RPC on the daemon socket with the new terminal handle IDs

The `register_panes` RPC stays: the handle type changes from tmux pane ids (strings like `%12`) to charm-internal terminal ids (UUIDs assigned by the Zed fork when creating each `TerminalView`). The daemon doesn't care about the handle format — it stores them as strings and echoes them back.

`charm stop`: stays the same — sends `shutdown` RPC to daemon socket, then quits the Zed fork process.

`charm resume`: becomes "reopen the Zed fork for this session, reconnect to the daemon, and reopen terminal tabs for any agents still alive." The daemon's `orchestrator_pane` RPC returns the orchestrator's terminal handle id; the Zed fork opens a new `TerminalView` running `claude --session-id <uuid> --resume` in the same working directory. No need for `tmux respawn-pane -k`.

### 7. Orchestrator Hub -> Zed

**GPUI supports multiple top-level windows.** `AppContext::open_window(WindowOptions, cx, |cx| view)` creates a new OS window. Each window has its own GPUI view tree.

**Two viable implementations:**

Option A — Separate GPUI window (mirrors Tauri's `WebviewWindow`):
```rust
let hub_window = cx.open_window(
    WindowOptions {
        title: Some("Charm Orchestrator Hub".into()),
        bounds: WindowBounds::Fixed(Bounds { size: size(px(800.), px(600.)) }),
        ..Default::default()
    },
    |cx| cx.new_view(|cx| OrchestratorHubView::new(cx)),
);
```
The `OrchestratorHubView` calls a new charmd RPC `list_sessions` (reads `.charm/run/*/meta.json`; see gap note below) to populate the session list.

Option B — In-window modal (simpler, no second OS window):
```rust
cx.open_modal(|modal, cx| {
    modal.child(OrchestratorHubModal::new(sessions, cx))
});
```
A modal overlays the current window and dismisses on session select or Escape.

**Recommendation:** Option B for the first iteration. It requires less surface area, avoids multi-window focus management, and the session count is typically small (1-3 concurrent sessions). Option A for a future "always visible" hub if multi-session becomes a primary workflow.

**Prerequisite gap:** charmd has no `list_sessions` RPC today (confirmed in T-024 and T-025). The Hub cannot be built until this RPC is added. It is a charmd-only change: enumerate `.charm/run/*/meta.json` files and return their contents. Low complexity; no daemon architecture change needed.

### 8. Approval gates UX

**Recommended: two-layer pattern.**

Layer 1 — Ambient: the `ApprovalsPanel` in the left dock is always visible and shows pending gates with Approve/Reject buttons. Badge count on the panel tab icon shows the pending count (equivalent to the Ink console auto-switching to the Approvals tab when `pendingCount > 0`).

Layer 2 — Modal on arrival: when a new gate enters the `ApprovalsState`, the `CharmSessionManager` fires:
```rust
cx.open_modal(|modal, cx| {
    modal.child(ApprovalGateModal::new(gate, cx))
          .on_dismiss(|_, cx| { /* user dismissed without deciding; gate stays pending in panel */ })
});
```
The modal shows: gate stage (2 = "Worker Plan" / 4 = "Diff"), the plan diff or description, and Approve/Reject buttons. Approve calls `approve_gate` RPC; Reject calls `reject_gate` (or `approve_gate` with `approved=false`). Modal dismissal without action leaves the gate pending in the panel.

This matches the Ink console's behavior: the TUI auto-switches to Approvals tab (Layer 2 equivalent), and the tab persists as ambient state (Layer 1 equivalent). The GPUI pattern maps cleanly.

**Why not notification banner?** A notification banner can be dismissed without deciding, which creates silent stuck pipelines. The modal enforces that the operator at minimum acknowledges the gate, even if they defer decision to the panel.

### Top 3 risks that need a prototype to resolve

**Risk 1: PTY text injection across process boundary (highest)**

The `inject_text` bridge socket approach requires the Zed fork to maintain a live `agent_id -> Terminal entity` registry, receive socket connections from charmd, and dispatch GPUI entity updates from a background thread. The specific unknown: does calling `terminal.update(cx, ...)` from a background `cx.background_executor()` task work correctly when the terminal PTY is mid-render? GPUI's entity system is thread-safe for reads but updates must go through `AsyncAppContext::update_entity()`. Validate this pattern with a standalone GPUI prototype before building the full session manager.

Also validate that `terminal.input(multi_line_bytes)` correctly handles the orchestrator's multi-line guidance messages. Tmux uses bracketed paste mode (`\x1b[200~...text...\x1b[201~`) to protect multi-line content. Zed's `Terminal::input()` does the same bracketed paste wrapping when the PTY is in bracketed-paste mode. If claude's REPL disables bracketed paste, bare injection may split on newlines. Test with real claude output before relying on this.

**Risk 2: Programmatic pane layout at session start (medium)**

Zed's workspace layout is designed to be user-driven (drag splits, resize handles). Programmatically creating a specific split arrangement at startup is possible (T-027 is investigating the exact Pane API) but may have edge cases: what if the user has previously resized the workspace, or a prior session's layout is persisted in Zed's state? Validate with a prototype that: (a) opens Zed to a project, (b) programmatically creates a left-dock panel + right pane split + canvas item, and (c) confirms the layout survives a window resize and re-focus cycle without collapsing.

**Risk 3: GPUI canvas animation at scale (medium)**

The `cx.request_animation_frame()` animation loop for traveling dots is standard GPUI pattern, but the full orchestration canvas — force-directed layout of 50+ nodes with live edge routing — has no performance baseline in this codebase. The unknown is whether GPUI's `paint_path()` calls for bezier edge curves at 60fps remain smooth when node count is high and layout is recomputed on every agent state change. A standalone `CharmCanvasElement` prototype (no full Zed integration, just the GPUI app) should validate: 50 nodes, 80 edges, 10 concurrent traveling dots, running on the target Apple Silicon machine. If frame time exceeds ~4ms, the force-directed layout update must be moved off the render path (compute layout in `background_executor`, push snapshot to the entity, paint from snapshot).
