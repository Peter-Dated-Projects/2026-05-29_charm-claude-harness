## Goal
Investigate how to ship over-the-air updates from a Rust desktop app. Use subagents to go deep on each mechanism in parallel.

## Mechanisms to investigate
1. **tauri-plugin-updater** — built-in Tauri updater, GitHub Releases / custom server, delta updates, code signing of update bundles
2. **self_update crate** — framework-agnostic, works with any binary
3. **msitools / Squirrel / WiX** — Windows installer-based update
4. **Sparkle / Homebrew Cask** — macOS-native patterns
5. **Custom: download + swap** — fetch new binary, verify signature, replace self at next launch
6. **Nix / Flatpak / AppImage auto-update** — Linux patterns

## For each mechanism
- Does it require a server? What does the server look like?
- How are update bundles signed? What key infrastructure is needed?
- Delta vs full-bundle updates — which support delta?
- Can it work offline-first (check on reconnect)?
- Integration complexity with each of the top Rust UI frameworks
- Any licensing or cost implications

## Specific charm requirements to validate
- The charm harness bundles a daemon (`charmd`) + UI + MCP server. An update must update all three atomically or gracefully.
- The daemon may be running during an update. How is the running process handled?
- Updates should be user-confirmable (not silent), consistent with the charm human-gated philosophy.

## Deliverable
A comparison table + recommended approach. Write to `.charm/proposals/PROP-ota-update-strategy.md`.
