### Discrepancy 1: Handle map diagram label says "TerminalView" but code holds `Entity<Terminal>`

All eight diagrams (architecture-diagram.mmd and the per-phase mermaid blocks in phases 0-7)
contain the node:

    handlemap["agent_id -> TerminalView map"]

But every code snippet that touches this map uses `Entity<Terminal>`:

- Phase 1 body: "The bridge keeps a map of `agent_id -> Entity<Terminal>` populated as agents spawn"
- Phase 4 body: "The bridge holds `agent_id -> Entity<Terminal>`"; `bridge.register_terminal(agent_id, terminal)`

`Terminal` and `TerminalView` are distinct Zed types. `Terminal` is the backend PTY entity
(the one with `input()` for text injection). `TerminalView` is the UI widget that wraps it.
The map must hold `Entity<Terminal>` to support `terminal.input()` injection.

Fix: In architecture-diagram.mmd and in every phase mermaid diagram, change:
    handlemap["agent_id -> TerminalView map"]
to:
    handlemap["agent_id -> Entity<Terminal> map"]

Blast radius: cosmetic-only, eight diagram files. No code is generated from the diagrams;
the code snippets are already correct.

### Discrepancy 2: `spawnAgentLocked` relay mechanism -- diagram implies push, only polling is defined

The architecture diagram (and all per-phase copies) shows:

    charmd ==>|"spawnAgentLocked"| bridge   (primary data flow, push-style arrow)

Phase 4 body says: "When the daemon fires `spawnAgentLocked` (relayed to the bridge), open
a new terminal in the agents pane."

But Phase 1 defines only a 1500ms polling loop on the `status` RPC. No phase defines how
the bridge detects that `spawnAgentLocked` has fired or how it triggers `spawn_task` on the
agents pane. The push-style diagram arrow is inconsistent with the polling-only implementation.

Two consistent resolutions:

Option A (polling diff): `CharmState.apply()` compares the incoming agent list against the
previous snapshot; for each new `agent_id` not previously present, it calls a registered
`on_agent_spawned` callback which opens the terminal. The diagram arrow should be relabeled
to show it travels through the status poll (`status` -> `apply` -> callback). No new daemon
code needed.

Option B (push extension): Add a push channel from daemon to bridge (one of the options
already listed in Phase 1 section "Daemon-side change" -- option a or b). Then the
`spawnAgentLocked` arrow in the diagram is accurate as-is. Requires new daemon code.

Option A is simpler and consistent with the polling-first approach. Recommendation: adopt
option A and update the diagram to show `spawnAgentLocked` is detected via the status diff
rather than a separate push.

The worker for Phase 1 must resolve this; it determines what `s.apply()` must do and
whether the bridge needs a spawn-callback registration API before Phase 4 can be built.

### Discrepancy 3: Phase 6 `Depends on` header references non-existent `ApprovalsPanel`

Phase 6 header:

    "(Earlier drafts and T-028 section 2 described a standalone left-dock ApprovalsPanel;
    that is superseded by the design's right-sidebar layout. There is no separate approvals
    panel.)"

`ApprovalsPanel` does not exist in the plan. Phase 6 depends on the Orchestrate tab inside
the right sidebar (Phase 2 `charm_sidebar.rs`), not on a standalone panel.

Fix: Change the Phase 6 header to:
    **Depends on:** Phase 2 (Orchestrate tab in right sidebar), Phase 1 (gate state)

### Discrepancy 4: `orchestrator_pane` RPC referenced in Phase 5 but never defined

Phase 5 body (`charm resume` detail):
    "open a fresh terminal tab in the agents (or orchestrator) pane running the resume
    command, and re-register its handle with the daemon via `orchestrator_pane`. The daemon
    side (`orchestrator_pane` RPC) is unchanged -- only the handle type differs."

This RPC name appears only in Phase 5. It is not listed in:
- The architecture diagram (no edge labeled `orchestrator_pane`)
- Phase 1's daemon-side section (which defines `register_panes`, `inject_text` options)
- Phase 4 (which defines `register_terminal` / `unregister_terminal` on the bridge)
- Any other phase

The claim "The daemon side (`orchestrator_pane` RPC) is unchanged" implies it already exists
in the daemon today. If it does, it is simply missing from the diagram and all other phases.
If it doesn't, it is a new undefined RPC.

Fix: Verify whether `orchestrator_pane` exists in `src/daemon/index.ts` (this is a daemon
code check, not in scope for this audit which reads proposal files only). If it exists, add
it to the architecture diagram. If it does not, Phase 5 needs to define it alongside the
`register_panes` RPC it already documents.

### Gap: Module names for Phases 3-7 in `crates/charm/` not specified

Phase 1 names `crates/charm/src/charm_bridge.rs`.
Phase 2 names `crates/charm/src/charm_explorer.rs` and `crates/charm/src/charm_sidebar.rs`.
Phases 3, 4, 5, 7 define structs (`OrchestrationItem`, `CanvasState`, `HubView`) but do not
name their source files within `crates/charm/`.

No contradictions found -- the named files are non-overlapping. But the crate module map is
incomplete, which may create ambiguity for a worker building Phase 3 through 7 about where
to put new code.

This is a gap, not an inconsistency. It can be resolved during Phase 1 scaffold by adding a
`crates/charm/src/lib.rs` (or `crates/charm/src/charm.rs`) that declares the expected
module structure upfront.
