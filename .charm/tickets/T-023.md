Investigate the Zed editor (https://zed.dev / https://github.com/zed-industries/zed) as a base for a custom multi-agent orchestration IDE.

Key questions to answer:
1. What is GPUI (Zed's GPU-accelerated Rust UI framework)? Can it be used independently from Zed as a UI toolkit for a custom app? What is its license?
2. What are Zed's three paths for customization: (a) build a Zed extension, (b) fork GPUI only, (c) fork Zed itself? Tradeoffs of each in terms of complexity, maintenance burden, and capability ceiling.
3. Does Zed have a plugin/extension system that could host a custom 'charm' panel showing the orchestration canvas (SVG node graph of agents/tickets/worktrees)? What can extensions render — are they full custom UI panels or just language/LSP-level?
4. What does Zed's extension API expose today? Can extensions spawn external processes, communicate over Unix sockets, read local files, and render custom SVG or HTML views?
5. Is there an active community of people who have forked Zed or GPUI to build custom editors? Any public examples?
6. What are the practical prerequisites for forking Zed (Rust toolchain, build times, platform targets: macOS/Linux/Windows)?
7. Compare against the current Tauri v2 + React approach already described in the charm studio HANDOFF.md: what does Zed give us that Tauri doesn't, and what does it cost?

Write your findings into this ticket body. Include concrete evidence — links to Zed docs, GitHub files, extension examples. Give a recommendation: which path (Zed extension vs GPUI fork vs full Zed fork vs stay on Tauri) best fits the goal of a fast, native, multi-agent orchestration IDE that needs to display a live animated agent graph, process tmux pane management, and communicate with the charm daemon over a Unix socket.

## Findings

### 1. What is GPUI?

GPUI is Zed's GPU-accelerated UI framework written in Rust. It uses Metal on macOS and Vulkan on Linux/Windows. It is a hybrid immediate/retained-mode framework: state is managed via typed `Entity<T>` handles, UI is declared via `Render` traits, and the GPU compositor does the final draw. It was designed to power Zed specifically; the Zed team considers it a core internal dependency but licenses it permissively to encourage external use.

**License:** Apache 2.0. This is separate from the Zed editor itself which is GPL-3.0. You can use GPUI in a proprietary product without GPL obligations. Sources: [zed.dev open source announcement](https://zed.dev/blog/zed-is-now-open-source), [gpui.rs](https://www.gpui.rs/), [crates/gpui README](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md).

**Independent use:** Technically yes, but with caveats. GPUI is not published to crates.io as a stable release. You must either (a) git-depend on the Zed monorepo and pick a commit, or (b) use a community fork like GPUI-CE. The API is unstable — the Zed team explicitly says breaking changes between versions are expected. The Zed codebase separates the low-level `gpui` crate from a Zed-specific `ui` crate; external projects use `gpui` directly and build their own component layer. The team has said they "would love to have help making gpui better and used more" (see [discussion #23812](https://github.com/zed-industries/zed/discussions/23812)).

### 2. Three customization paths and tradeoffs

#### (a) Build a Zed extension

Extensions run as WebAssembly in a Wasmtime sandbox. They can provide: languages, themes, debuggers, snippets, slash commands, MCP servers. The extension API capabilities are governed by an explicit capability system.

**What extensions CAN do** ([docs/extensions/capabilities](https://zed.dev/docs/extensions/capabilities)):
- Spawn external processes (`process:exec` capability) — invoke commands with configurable argument restrictions
- Download files from remote hosts (`download_file`)
- Install npm packages (`npm:install`)
- Register MCP servers (which can then communicate over stdio or HTTP with external processes)

**What extensions CANNOT do:**
- Access the local filesystem directly (WASM sandbox blocks this)
- Communicate via Unix sockets (no capability exists)
- Render custom UI panels or views — confirmed absent from the API
- Embed a webview (HTML/SVG in a browser pane) — this is an open feature request ([issue #21208](https://github.com/zed-industries/zed/issues/21208), status: triage, no assignee, no timeline)
- Access GPUI internals, the GPU context, the element tree, or the window handle

**Verdict for charm:** Extension path is a hard no for the orchestration canvas. The charm panel needs to render a live animated SVG node graph, communicate with the daemon over a Unix socket, and manage tmux panes. None of these are possible from within a Zed extension today. The webview issue has been open since November 2024 with no progress.

Complexity: Low. Maintenance burden: Low. Capability ceiling: Too low for charm's needs.

#### (b) Fork GPUI only (use as a standalone library)

Use GPUI as a Rust UI framework — not Zed the editor — to build charm studio from scratch.

**Pros:**
- Apache 2 license: cleanest IP story, no copyleft burden
- Active community: see awesome-gpui ([github.com/zed-industries/awesome-gpui](https://github.com/zed-industries/awesome-gpui)) with 30+ applications already built (Termy terminal emulator, Fulgur text editor, Zedis Redis GUI, Vellum markdown editor, etc.)
- GPUI-CE community fork ([github.com/gpui-ce/gpui-ce](https://github.com/gpui-ce/gpui-ce)) focuses on general-use cases, 686 stars, active Discord
- gpui-component library ([github.com/longbridge/gpui-component](https://github.com/longbridge/gpui-component)) provides 60+ cross-platform desktop widgets
- Glass-HQ fork ([github.com/Glass-HQ/gpui](https://github.com/Glass-HQ/gpui)) targets iOS, web, Windows beyond what Zed ships
- Rendering quality is production-grade (Zed itself ships to millions of users on this stack)

**Cons:**
- You build the entire UI layer. Terminal widget (~1,000-2,000 lines of Rust; `alacritty_terminal` crate handles the model, rendering is DIY), force-directed graph rendering (no ready crate; must implement in GPUI's element API), diff view (no ready crate).
- No stable crates.io release — must git-dep or vendor.
- API breaks between Zed releases. Tracking upstream means periodic migration work.
- No webview embedding in GPUI (it's GPU-native, not a browser). An animated SVG graph must be drawn via GPUI's own element/path APIs.
- Requires a Rust engineer who is comfortable with GPU UI programming. The learning curve is steeper than egui.

Complexity: High (build everything). Maintenance burden: Medium (API churn from upstream). Capability ceiling: High — production-grade native app with no limitations on what you render.

#### (c) Fork Zed itself

Fork the full Zed repository and reshape it into the charm IDE.

**Pros:**
- You inherit all of Zed's existing widgets: terminal (built on `alacritty_terminal`), diff editor (via `language::Buffer` + tree-sitter), LSP integration, pane management, command palette.
- Proven, production-quality codebase used by a large active user base.

**Cons:**
- License: Zed editor is GPL-3.0. Your fork must also be GPL-3.0, which means distributing the source. If charm studio is to be a commercial product, you would need a commercial license negotiation with Zed Industries.
- Codebase size: Zed is ~700k+ lines of Rust across ~200+ crates. Understanding and adapting it is a multi-month effort even for experienced Rust engineers.
- Upstream divergence: Zed ships frequent releases. Staying in sync (or choosing not to) is an ongoing cost either way.
- You inherit features you don't need (LSP, collaborative editing, remote development) that add compile-time and binary-size weight.
- Adding charm-specific UI (the orchestration canvas, ticket graph, agent pane) requires understanding Zed's internal workspace/pane architecture before you can extend it.

Complexity: Very high. Maintenance burden: Very high. Capability ceiling: Highest, but most of the capability is Zed-specific and irrelevant to charm.

### 3. Extension rendering for the charm panel

Confirmed no. See finding #2(a). Extensions cannot render custom panels today. The internal discussion ([#37270](https://github.com/zed-industries/zed/discussions/37270)) proposes a `CustomViewProvider` trait that would give extensions a curated set of GPUI widget primitives (tables, text, tree views, toolbars) via a declarative protocol — but this API does not exist in shipping Zed as of mid-2026. Webview (HTML in an embedded browser, which would let you render SVG) is issue #21208, open and untriaged.

### 4. Extension API — specific capabilities for charm's use case

| Requirement | Extension capable? | Notes |
|---|---|---|
| Spawn external processes | Yes (`process:exec`) | Restricted by capability declarations in extension.toml |
| Unix socket communication | No | Not exposed; MCP server extensions use stdio or HTTP, not raw sockets |
| Read local files | No | WASM sandbox; no filesystem capability |
| Render SVG/HTML panel | No | No webview; no custom GPUI element access |
| Communicate with charm daemon | No (directly) | Could register an MCP server that proxies over HTTP, but loses low-latency Unix socket path |

### 5. Community ecosystem

Active and growing, specifically around GPUI-as-library (path b), not Zed-as-editor forks (path c).

Key projects confirmed:
- [awesome-gpui](https://github.com/zed-industries/awesome-gpui): curated list of 30+ GPUI apps (terminals, editors, DAWs, database GUIs, browser, clipboard managers)
- [gpui-ce](https://github.com/gpui-ce/gpui-ce): community edition fork, general-purpose focus, 686 stars
- [gpui-component](https://github.com/longbridge/gpui-component): 60+ widget component library
- [create-gpui-app](https://github.com/zed-industries/awesome-gpui): scaffolding tool for new GPUI projects
- [gpui-book](https://github.com/zed-industries/awesome-gpui): documentation book

There are no prominent public examples of full Zed forks being used as custom IDEs — the community gravitates toward using GPUI as a library.

### 6. Build prerequisites

| Requirement | Details |
|---|---|
| Rust toolchain | Latest stable Rust required; MSRV not pinned, tracks stable |
| C/C++ compiler | Required (clang on macOS, gcc on Linux) |
| macOS | Xcode (for Metal SDK) |
| Linux | libxkbcommon-dev, wayland-dev (Ubuntu/Debian); libxkbcommon-devel, wayland-devel (Fedora) |
| Windows | Windows 10 1809+, Vulkan-capable GPU drivers |
| First build time | 10-15 minutes (full Rust compile of Zed's ~200 crates) |
| Platform targets | macOS (Metal), Linux (Vulkan/Wayland/X11), Windows (Vulkan, added 2024) |

For a GPUI-only fork, first build is faster (~3-5 min) since you're not compiling all of Zed's language/LSP/collaboration crates.

### 7. Zed vs Tauri v2 + React for charm studio

The KB already has three directly relevant decisions (see `decisions/0005-rust-ui-framework-ecosystem-gap.md`, `decisions/spatial-canvas-ui-feasibility.md`, `decisions/vscode-layout-rust-feasibility.md`). This investigation confirms and extends those findings.

| Dimension | Zed extension | GPUI fork (library) | Full Zed fork | Tauri v2 + React |
|---|---|---|---|---|
| Animated agent graph | No (no SVG/canvas render) | Yes (build via GPUI element API, ~2-3 weeks) | Yes (build via GPUI, ~2-3 weeks inside Zed arch) | Yes — D3 / vis-network / @antv/layout, ready in days |
| tmux pane management | No direct access | Yes (Unix socket to daemon from Rust backend) | Yes | Yes (Rust backend via Tauri commands; same Unix socket) |
| Unix socket daemon comm | No | Yes (native Rust) | Yes (native Rust) | Yes (Rust backend layer) |
| Terminal emulation | No | Build required (alacritty_terminal + widget, ~1-2k lines) | Inherited from Zed | xterm.js — drop-in, zero build |
| Diff view widget | No | Build required | Inherited from Zed | react-diff-viewer / monaco — drop-in |
| License | Apache 2 (extension code is yours) | Apache 2 (GPUI) | GPL-3.0 (must open source or license) | MIT (Tauri) |
| UI iteration speed | N/A | Slow (Rust compile cycle, ~30-60s incremental) | Slow | Fast (Vite HMR, instant) |
| Startup time | Inside Zed (instant) | ~50-150ms (native, no WebView) | ~50-150ms | 400-800ms (WebView init) |
| Distribution | Zed plugin store | Self-hosted binary | Self-hosted binary | Self-hosted binary (Tauri bundles) |
| Viable for charm today | No | In 4-6 weeks if Rust engineer available | In 8-12 weeks + GPL constraint | Yes — already the planned path |

**What Zed (GPUI fork) gives over Tauri:**
- Faster startup (~100ms vs ~600ms)
- No WebView memory overhead (~150MB vs ~350MB process footprint)
- Tighter macOS integration (native menus, native text rendering, system font stack via Core Text)
- The charm agent graph drawn at 60fps via GPU compositor with no browser frame budget concerns

**What Zed costs over Tauri:**
- Every widget charm needs (terminal, diff, graph canvas) must be built in Rust — no ready ecosystem
- Slower UI iteration cycle (Rust compilation vs Vite HMR)
- No crates.io stable release; API instability requires version pinning
- Higher hiring bar (Rust GPU UI is a specialized skill)

## Recommendation

**Stay on Tauri v2 + React. Do not adopt Zed or GPUI at charm's current stage.**

The Zed extension path is ruled out immediately — it cannot render custom panels, access Unix sockets, or embed SVG. That is a hard technical blocker, not a prioritization call.

The GPUI-fork path is viable in principle but requires 4-8 weeks of widget-building before it matches the capabilities charm already has in its Tauri plan. The prior KB decision (`0005-rust-ui-framework-ecosystem-gap.md`) correctly identifies this: the gap is not Rust's rendering quality, it's the absence of ready-made widgets for terminal emulation, diff views, and force-directed graph rendering. The GPUI community is active and growing, but those specific widgets still need to be built.

The full Zed fork adds a GPL license complication on top of the widget-building cost. If charm becomes a commercial product this is a material legal risk.

**If the charm native IDE ever becomes a serious priority:** GPUI-as-library (path b) is the right long-term call — not a Zed fork. The community is there (gpui-ce, gpui-component, gpui-book), the license is clean, and the performance ceiling is real. Revisit when charm has a dedicated Rust engineer, when UI requirements are stable enough to justify the widget investment, and when distribution to non-terminal users is imminent. The trigger conditions from `decisions/spatial-canvas-ui-feasibility.md` remain accurate: revisit when charm is used by non-terminal operators or concurrent ticket count routinely exceeds ~50.

For the near term, close the Ink/console gaps in TypeScript, then follow the Tauri Track B plan from `decisions/prop-ui-revamp-feasibility.md` when distribution becomes the priority.
