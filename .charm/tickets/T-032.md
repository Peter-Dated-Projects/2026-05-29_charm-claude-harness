GOAL: Verify the 8-phase Zed-fork plan (phase-0 through phase-7) forms a coherent, buildable sequence with no dependency contradictions.

READ: `.charm/proposals/PROP-zed-fork-build-plan/README.md`, every `phase-*.md` file in that folder, and `architecture-diagram.mmd`.

CHECKS:
1. Build the dependency graph from each phase's `Depends on:` and `Blocks:` header lines. Validate it is a DAG: no cycles, no forward references (a phase must not depend on a later phase's output unless intentional).
2. Does each phase only rely on capabilities built in EARLIER phases? Flag any phase that uses something not yet built at that point in the sequence.
3. Strip-vs-need: cross-check Phase 0's crate removal list against the `Source:` lines and technical content of phases 1-7. Does any later phase depend on a crate or feature that Phase 0 strips/deletes? (e.g. an AI/collab/edit-prediction crate.)
4. Mutual consistency: if phase A says it `Blocks:` B, does B's `Depends on:` list A (and vice versa)? Flag asymmetries.

DELIVERABLE: Write findings into this ticket body AND `.charm/kb/zed-phase-consistency-deps.md`: the validated dependency graph (as text), every cycle/gap/contradiction/asymmetry found, and a concrete recommended fix for each. ASCII only, no emoji.

## Findings

Full detail in `.charm/kb/zed-phase-consistency-deps.md`. Summary below.

### Validated dependency graph

```
P0  depends on: (nothing)
P1  depends on: P0
P2  depends on: P1
P3  depends on: P1
P4  depends on: P1
P5  depends on: P1, P2, P3, P4
P6  depends on: P1, P2
P7  depends on: P1
```

Topological order: P0 -> P1 -> P2/P3/P4 (parallel) -> P6 (after P2 only) -> P5 (after P2-P4) -> P7 (after P1 only)

### Check 1: DAG -- PASS

No cycles. No forward references. Clean directed graph.

### Check 2: Capability-before-use -- PASS

Every phase consumes only capabilities built in earlier phases. Phases 1-7 use only crates that Phase 0 explicitly keeps (terminal, terminal_view, workspace, gpui, etc.). No phase reads from a crate on the strip list.

### Check 3: Strip-vs-need -- PASS

No later phase needs a stripped crate. Pre-existing gotcha (already noted in Phase 0): `agent_settings` needs an audit-before-delete because it may be referenced by kept crates' inline-assist paths. This is flagged in Phase 0 and does not represent a plan-level contradiction.

### Check 4: Mutual consistency -- 3 ISSUES

**Issue 1 (significant): Phase 1 Blocks under-declares**

Phase 1 header says `Blocks: Phases 2, 3, 4` but Phases 5, 6, and 7 also directly list Phase 1 in their Depends on. The Blocks list should be Phases 2, 3, 4, 5, 6, 7.

Fix: Update Phase 1 header to `Blocks: Phases 2, 3, 4, 5, 6, 7`.

**Issue 2 (significant): Phase 6 Depends-on names a scrapped component**

Phase 6 header: `Depends on: Phase 2 (ApprovalsPanel), Phase 1 (gate state)`. Phase 2 does not build an ApprovalsPanel -- that design was superseded by the inline banner inside the Orchestrate tab. The dependency on Phase 2 is correct; the stated reason is stale.

Fix: Update Phase 6 header to `Depends on: Phase 2 (Orchestrate tab -- hosts the inline gate banner), Phase 1 (gate state)`.

**Issue 3 (documentation): Phase 0 "Blocks: every other phase" over-claims**

Phase 0 directly blocks only Phase 1. Phases 2-7 depend on Phase 0 transitively through Phase 1, not directly. The claim is logically true but causes a false symmetry expectation: readers expect phases 2-7 to list Phase 0 in their Depends on, and they don't.

Fix: Change Phase 0 to `Blocks: Phase 1` with a note that the transitive effect covers all subsequent phases.

### Additional gaps (not contradictions)

**Finding 4:** README says "Phases 5-7 are polish" grouping them as a sequential tail. Phase 6 only requires Phases 1 and 2 (not 3 or 4) and can start in parallel with Phases 3 and 4. Phase 7 only requires Phase 1. A team following the README may unnecessarily serialize these. Fix: add per-phase parallelism notes to the README table.

**Finding 5:** Phase 5 declares `Depends on: Phases 1-4` but Phase 3 (the optional orchestration tab) is opened on demand post-boot -- Phase 5's auto-detect does not need it to be complete. This is an over-declaration that creates a false serial constraint. Fix: change to `Depends on: Phases 1, 2, 4` with a note that Phase 3 is independently openable.
