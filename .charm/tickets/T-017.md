## Goal
For every feature the current charm harness has, determine if each top Rust UI framework can support it. This is the definitive 'can we actually ship this' check. Use subagents to audit each feature area in parallel.

## Current charm features to map

### Console / UI
- Three-tab terminal UI (Artifacts, Approvals, Agents)
- Markdown viewer with live file watching
- Keyboard navigation (vim bindings, tab switching)
- Mouse wheel scrolling
- Agent status grid (live-updating, 1500ms poll)
- Force-directed KB graph (separate OS window today)
- Approval gate: y/n keyboard confirm
- Kill agent with two-press guard

### Daemon / backend
- Unix domain socket JSON-RPC server
- SQLite-backed ticket store with frontmatter round-trip
- tmux session management (spawn panes, send keys, kill panes)
- Agent process spawning (`charm-claude` sessions)
- COORDINATION.md file writer
- Orchestrator ping coalescing (1200ms debounce)
- Dependency + touches conflict resolver

### MCP server
- stdio JSON-RPC protocol (Claude Code bridge)
- 20+ tool definitions forwarded to daemon
- Per-agent ID injection

### Distribution / ops
- Single `charm` CLI entry point
- `charm init`, `charm start`, `charm stop`, `charm attach` subcommands
- Per-session UUID and socket path layout
- OTA update (desired, not yet built)

## For each framework (Tauri, Dioxus, GPUI, Slint, Iced, egui)
- Which features are native/easy?
- Which need crates that may or may not exist?
- Which are blockers (no clear path)?
- Specific gap: tmux management from a GUI app — is that a problem?
- Specific gap: Unix socket RPC from the UI process — easy in all?

## Deliverable
A binary/partial/blocked compatibility table. Write to `.charm/proposals/PROP-feature-compatibility-matrix.md`.
